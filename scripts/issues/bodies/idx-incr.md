## 背景

全量索引即便优化到 [[idx-perf]] 的目标，大型项目也要 90 s、中型项目 40 s 左右。而 M0 实测：**中型测试项目在 1 小时内改动了 790 个文件**（`M0_LANG_SPIKE_REPORT` 的"csproj 过期"一条），AI 工具批量改代码的场景只会更频繁。该报告的"对设计文档的修正"已经把增量更新的优先级提高为"M2 必须做"。

做法见 `LANGUAGE_INTELLIGENCE` §3.3 的"增量更新"：索引进程增加常驻模式，文件保存后用 Roslyn 的增量编译只重绑这一个文件，产出一个小的**覆盖层**段；Rove 侧查询时把"基础索引 + 覆盖层"合并起来看。目标是单文件更新 < 300 ms（§6 验证计划）。

本 issue 同时涉及 .NET 侧（常驻进程、重绑、覆盖层生成）和 Rust 侧（`crates/rove-lang-cs`，覆盖层的读取与合并）。Rust 侧的查询接口形状由 [[contracts]] 定义、[[router]] 使用，本 PR 不改接口。

## 目标

### 1. 常驻模式与协议

索引进程增加常驻模式：与 Rove 通过 **stdin/stdout 上的 JSON-RPC 或命名管道**通信（选哪种要在 PR 中说明理由；进程由 [[idx-life]] 拉起与监控）。至少支持这些消息：

- 全量索引（带进度上报）；
- "文件 X 已变更 / 已删除 / 新增"；
- "查询当前状态"（正在更新哪些文件、覆盖层数量）；
- 关闭。

**空闲 N 分钟后自动退出**（N 可配，默认值在 PR 中给出依据），退出前把覆盖层落盘。协议第一条消息是版本握手——握手的具体规则与版本协商由 [[idx-pack]] 定稿，本 issue 只要在协议里**预留握手消息**，并保证版本字段在第一条消息里。

### 2. 单文件重绑

用 Roslyn 的增量编译（`WithChangedText` / `ReplaceSyntaxTree`）重新绑定变更的文件，收集"该文件发出的引用"和"该文件声明的符号"。注意两个 M0 已经踩过的坑：

- **预处理宏必须在解析时生效**，用该文件所属项目的 `DefineConstants` 重新解析（`M0_LANG_SPIKE_REPORT` 发现的问题第 2 条，这一条曾把未解析率从 0.19% 拉到 0.035%）；
- **文件可能被 Unity 编辑器或杀毒软件独占**，以共享模式读取并重试（同报告第 3 条）。

### 3. 覆盖层

重绑结果写成一个独立的覆盖层段：替换该文件的全部出现位置，并更新它声明的符号。要求：

- 覆盖层可以单独追加写入，不重写基础索引；
- 合并后的查询仍然是 **O(log n)**（覆盖层数量有上限，见第 5 条）；
- 删除文件时写一个"该文件已清空"的覆盖层，不要留下悬空的出现位置。

### 4. 影响分析

如果某个文件声明的符号的**签名或可见性**变了，引用了这些符号的其他文件的绑定结果可能也变了。把这些文件加入后台重建队列逐步重绑（按引用表反查即可，索引里已经有这个信息）。后台重建要可取消、可限速，不能把常驻进程的 CPU 吃满。

### 5. Rust 侧：合并与全量重建

`crates/rove-lang-cs`：

- 查询时合并基础索引与全部覆盖层（后写的覆盖层优先）；
- 覆盖层数量或总体积超过阈值时，**触发后台全量重建，完成后原子替换**（替换的落地动作在 [[idx-life]]，本 issue 负责给出"该重建了"的信号与阈值）；
- 合并逻辑要有单元测试，不依赖真实项目也能跑（用构造出来的小索引 + 覆盖层）。

### 6. 项目结构变化

`.asmdef` / `.asmref` / `.csproj` 发生变化时，项目模型本身要重建，**直接降级为全量重建**，不要试图做增量（`LANGUAGE_INTELLIGENCE` §3.3）。

## 不包含

- 缓存目录、有效性检查、拉起与监控进程、原子替换的落地、文件事件的来源（全部是 [[idx-life]]）。
- 索引格式的段布局与头部字段（[[idx-format]]，本 issue 使用它预留的覆盖层字段）。
- 元数据视图的重建：DLL 没变时视图不需要重建，在 PR 中说明这个前提（[[idx-meta]]）。
- 版本握手的策略与组件打包（[[idx-pack]]）。
- 界面上的"增量更新中"状态（[[idx-life]] 的状态栏条目）。

## 验收标准

- [ ] 大型项目（`ROVE_TEST_UNITY_LARGE`）：保存一个普通 `.cs` 文件后，该文件的跳转与引用在 **< 300 ms** 内更新（给出 p50 / p99，至少 50 次采样）
- [ ] 修改一个方法签名后，其他文件中对它的引用在后台重建完成后得到更新，有测试覆盖
- [ ] **一致性测试：对大型项目连续做 1000 次随机编辑（插入、删除、改签名、新增文件、删除文件），增量后的索引查询结果与全量重建的结果完全一致**
- [ ] 删除文件、新增文件、文件重命名三种情况各有用例
- [ ] `.asmdef` / `.csproj` 变化时降级为全量重建，有测试
- [ ] 常驻进程空闲时的内存占用与自动退出行为有测量数据（空闲内存应远低于全量索引的峰值）
- [ ] 覆盖层数量达到阈值时触发后台全量重建；重建期间旧索引仍可查询，有测试
- [ ] 文件被独占打开时重试成功，不中断常驻进程
- [ ] Rust 侧"基础索引 + 覆盖层"的合并有不依赖真实项目的单元测试；合并后查询仍为 O(log n)（用一个覆盖层数量递增的基准证明）
- [ ] 常驻进程不发起任何网络请求
- [ ] 新增集成测试覆盖"启动常驻进程 → 通知文件变更 → 查询得到新结果 → 关闭"；[[skeleton]] 的端到端测试继续通过

## 风险与提示

- **一致性是这个 issue 的核心价值，也是最容易出问题的地方**。增量结果和全量结果不一致时，用户看到的是"跳错了地方"，比"跳不过去"更糟。1000 次随机编辑的一致性测试要能自动复现（固定随机种子并打印），发现不一致时能精确定位到哪一次编辑。
- 影响分析很容易写成"保守地把一切都重建"（等于没做增量）或"乐观地什么都不重建"（等于结果错）。先从"签名或可见性变化"这一条明确规则做起，把判定逻辑单独写成可测的函数。
- **索引进程的文件按 [[idx-format]] → [[idx-perf]] → [[idx-meta]] → [[idx-incr]] 的顺序串行修改**（依赖图已保证这个顺序：[[idx-incr]] 依赖 [[idx-meta]]），因为它们都要改 `tools/rove-indexer-cs/Program.cs`。
- 常驻进程的生命周期由 [[idx-life]] 管，协议由 [[idx-pack]] 定版本。三方的边界在开工前就要对齐：**本 issue 定消息内容，[[idx-life]] 定何时启停，[[idx-pack]] 定版本如何协商**。
- 增量更新带来的"部分文件是新的、部分是旧的"状态，会让 [[router]] 的位置映射更复杂。本 issue 要向 [[router]] 明确暴露"某个文件在索引中的版本"（内容哈希），不要让它去猜。
