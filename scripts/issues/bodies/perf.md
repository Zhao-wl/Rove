## 背景

Rove 的核心定位是性能（`PROJECT_CHARTER` §6）。性能退化必须在 PR 阶段被发现，不能等到发版。M0 还留下了一个必须长期盯住的结论：**当可见行全部需要重新整形时，GPUI 与自研栈都守不住 120 fps**（帧间隔 p99 约 16.8 ms，见 `M0_UI_SPIKE_REPORT` §4.4 与 §7 约束 3）。所以基准里必须有"整形缓存全未命中"这一组，而不只是乐观场景。

本 issue 只建设施与预算，不做具体优化；各 issue 的优化在各自 PR 中接入这里的基准。

## 目标

### 1. 测试数据生成

把 `spikes/gen_testdata.py` 移植为 `cargo xtask gen-testdata`，生成到被 gitignore 的目录（规格照搬 `M0_UI_SPIKE_REPORT` §2.5，保证与 M0 数据可比）：

| 文件 | 规格 | 用途 |
|---|---|---|
| `small.txt` | 46 KB / 402 行，7 种模式循环（纯 ASCII、中文、中英混排 + emoji 含 ZWJ 与肤色修饰、日韩、tab 缩进、300 字符长行） | 整形缓存命中时的乐观值、字体回退 |
| `big1g.txt` | 1 GiB / 1429 万行，类 C# 代码，每 50 行一行中文 | 大文件打开与滚动、行索引 |
| `uniq.txt` | 33 MB / 40 万行，**每行文本都唯一** | 整形缓存全未命中的真实成本 |

### 2. 基准框架

各 crate 下用 `criterion` 写基准，统一入口 `cargo xtask bench`。基准必须**只依赖 [[contracts]] 的接口**，不得为了测量绕过接口或在接口上开后门。

### 3. 预算文件 `perf/budgets.toml`

把 `PROJECT_CHARTER` §6 写成机器可读的预算：

- 冷启动到可交互 < 400 ms（2026-11-09 修订值）。“可交互”的定义：**首帧已呈现，且第一个输入事件能在一帧内得到响应**。M0 实测的 396 ms 只到首帧，按新口径可能略超，以实测为准
- 冷启动到首帧：单独记录，不设门槛（作为“可交互”的拆分数据）
- 空窗口常驻内存 < 60 MB（M0 实测工作集 47.7 MB）
- 打开 1 GB 文本文件 < 1 s（M0 实测首屏 444 ms）
- 按键到上屏 < 8 ms
- 定义跳转 < 16 ms、查找引用 < 50 ms（语义索引就绪时）
- 每帧 CPU < 1 ms（`FEATURES` §1；M0 的 GPUI 原型在 `uniq.txt` 上是 4279 µs，差距要在 [[codeview]] 中补上）

每条预算注明"由哪个 issue 负责达标"，暂时达不到的标为 `pending` 并写明原因，不允许静默降低数值。

### 3.1 体积守护（从 M1 起）

每个 PR 报告 `rove.exe` 的体积及相对基线的变化（基线：M0 实测 6.2 MB），超过预算时 CI 失败。预算值写进 `perf/budgets.toml`。立项指标是发布包 < 30 MB（`PROJECT_CHARTER.md` §6）；发布包的完整组成到 [[release]] 才确定，届时由它把检查对象扩展到整个发布包。

### 4. 采集口径

写进 `perf/README.md`：冷启动分两个时间点记录——“首帧已呈现”（与 M0 口径一致）和“可交互”（在首帧之后自动注入一个按键，记录它被处理并重新绘制完成的时刻）；预算按“可交互”考核；每帧 CPU **不含** swapchain acquire / present 的 vsync 阻塞（M0 §2.5 记录过一次因口径错误把 149 µs 读成 7.2 ms 的教训）；内存区分工作集与私有提交（1 GB 文件的工作集包含 mmap 的文件页，不等于真实占用）。[[skeleton]] 已在日志中记录"进程启动 → 首帧"的时间，这里负责把它采集成指标。

### 5. CI 中的相对比较

一个可手动触发、或在带 `perf` 标签的 PR 上运行的任务：与 `main` 跑同一组基准并比较，退化超过 15% 时报警。**不做绝对判定**（托管机器波动大）。绝对指标在本地参考设备上测量并记入报告。

## 不包含

- 任何具体的性能优化（在各自 issue 中做）。
- 发布包体积守护（[[release]]）。
- 冷启动的火焰图拆解（`M0_UI_SPIKE_REPORT` §7 约束 4 的那一项，归 [[shell]] 的启动预算）。

## 验收标准

- [ ] 冷启动同时报告“首帧”与“可交互”两个时间，预算按“可交互”判定
- [ ] 每个 PR 都能看到 `rove.exe` 的体积变化；人为加入一个大文件使体积超过预算时 CI 失败
- [ ] `cargo xtask gen-testdata` 产出三个文件，大小与行数与 M0 一致（误差 < 1%）
- [ ] `cargo xtask bench` 可用，至少接入三组基准：`rove-buffer` 打开文件、`rove-workspace` 扫描、`rove-lang-cs` 已有的索引查询
- [ ] `perf/budgets.toml` 覆盖 `PROJECT_CHARTER` §6 的全部指标，每条都有负责的 issue
- [ ] 超预算时 `cargo xtask bench --check-budgets` 以非零码退出，并打印超出的项与幅度
- [ ] `uniq.txt` 的"全唯一行滚动"是一条正式基准用例（即便 [[codeview]] 未完成也先占位）
- [ ] CI 的相对比较任务能跑通一次，并在 PR 中贴出对比表
- [ ] `AGENTS.md` 补充"涉及性能的 PR 必须附基准数据"的具体做法（与 [[ci]] 协调）

## 风险与提示

- **机器差异**：参考设备是 8 核 / 16 GB / SSD / 集显，而开发机是 16 核 + 独显 + D 盘机械硬盘。同一份数字在两台机器上的含义不同，报告里必须写清测量环境。
- 基准数据文件很大（1 GiB），不要提交，也不要在 CI 上生成 `big1g.txt`；CI 任务只跑小数据和 `uniq.txt` 级别的用例。
- 预算是用来约束设计的，不是用来事后解释的。某项指标确实需要修订时，走 `PROJECT_CHARTER` 的修订流程（像冷启动从 150 ms 改到 400 ms 那样留下记录），不要直接改 `budgets.toml`。
