## 背景

三层结构（L2 精确语义索引、L1 快速声明索引、L0 语法层）各自能回答一部分问题，**决定该问谁、并把结果翻译回用户当前看到的坐标**，是本 issue 的事。路由规则在 `LANGUAGE_INTELLIGENCE` §3.2：

```
请求（文件, 位置）
  ├─ 文件内容与 L2 索引时的版本一致？
  │     是 → 查 L2 → 精确结果
  │     否 → 已修改文件做位置映射（按文本 diff 平移行列）
  │            ├─ 映射成功且该符号所在区域未被修改 → 查 L2
  │            └─ 否则 → L0/L1 回退，结果标记为"近似"，
  │                     并触发该文件的增量重建
  └─ L2 尚未建好 → L0/L1 回退，界面提示"语义索引构建中 xx%"
```

核心原则是 §3.2 最后那句：**用户总能立即得到结果；L2 就绪后，结果自动变为精确**。Rove 以阅读为主、编辑为辅，所以"正在编辑但未保存的区域精度下降"是设计上接受的代价（§4 代价第 2 条）。

本 issue 在 `crates/rove-lang-cs` 中实现统一的查询 API，**放在 [[contracts]] 定义的 C# 导航查询接口背后**（定义、引用、实现、悬停、符号，结果带精确度：精确 / 近似 / 语法）。它是 [[nav-ui]]、[[peek]]、[[meta-ui]] 的唯一数据入口；**本 PR 不修改这些接口**，确需修改时按契约变更流程单独提 PR。

## 目标

### 1. 统一查询 API

实现 [[contracts]] 的 C# 导航查询接口：

- 转到定义（可能多个候选，例如 `partial`）；
- 查找引用（区分读 / 写 / 调用，索引里已有 role 字段）；
- 查找实现 / 重写 / 派生（用索引的关系表）；
- 悬停：签名 + 文档注释；
- 文件内符号与工作区符号。

**每个结果都带精确度标记**：精确（L2）/ 近似（L1）/ 语法（L0）。精确度是逐结果的，不是逐请求的——一次查询里可以既有精确结果也有近似结果（[[nav-ui]] 按 `UX_SPEC` §2.2 决定怎么提示）。接口是同步的（M0 实测 L2 查表 avg 2–4 µs），但不得在界面线程上做 I/O。

### 2. 版本判定与位置映射

- 从 [[idx-life]] 取"某个文件在索引中的版本"（内容哈希），与 [[buffer]] 当前缓冲区的版本比对；
- 不一致时，按缓冲区与索引版本之间的**文本差异平移行列**，把查询位置映射回索引时的位置；
- **映射成功，并且目标符号所在的区域没有被修改** → 查 L2，结果仍是精确；
- 否则回退 L1/L0，结果标记为"近似"，并通知 [[idx-life]] / [[idx-incr]] 触发该文件的增量重建。

"该区域是否被修改"的判定粒度要定清楚（行级还是语句级）并写进 PR——定得太粗会白白丢掉精度，太细又可能把改过的地方当成没改。

### 3. 反向映射

L2 返回的位置如果落在**已修改但未保存的文件**里，要按同样的差异平移到当前缓冲区中的位置，否则跳转会偏行。引用列表里可能同时包含干净文件和脏缓冲区中的位置，两种都要处理。

### 4. L0 兜底：局部变量与参数

文件内的局部变量、参数、局部函数、lambda 参数，在 L2 不可用（未就绪 / 已修改 / 组件未安装）时由 **L0 的 tree-sitter 作用域分析**兜底：在当前文件的语法树上做作用域查找，结果标记为"语法"。这一类符号本来就只在单个文件内有意义，L0 能做得相当准。

### 5. 降级路径

- L2 未就绪或组件未安装 → L1/L0，并对外报告"构建中 xx%"供状态显示（[[idx-life]]）；
- 外部符号 → 指向 [[idx-meta]] 生成的元数据视图位置（[[meta-ui]] 负责打开）；
- 什么都查不到时返回空结果，**不要返回一个看起来像答案的错误结果**。

## 不包含

- 查询接口的定义本身（[[contracts]]）。
- L1 的构建与查询实现（[[l1]]）、L2 的格式与生命周期（[[idx-format]]、[[idx-life]]）、增量重建（[[idx-incr]]）。
- 任何界面：转到定义、Ctrl+点击、悬停卡片、导航历史、近似结果提示（[[nav-ui]]）；速览窗口（[[peek]]）；元数据视图（[[meta-ui]]）。
- 语义级同名高亮（[[nav-ui]]）、语义高亮（[[semantic]]）。
- 编辑、撤销与保存（M3）。

## 风险与提示

- **位置映射是本 issue 最容易出错也最影响体验的部分**。跳转偏了一两行，用户不会怀疑是映射的问题，只会觉得"这个编辑器不准"。先把映射写成一个纯函数（输入：索引版本的文本与当前文本的差异、一个位置；输出：映射后的位置或"落在修改区内"），单独做属性测试，再接进路由。
- 不要用整文件 diff 来做映射。缓冲区已经知道自己发生过哪些编辑（[[buffer]] / [[edit-core]] 的编辑事务），按编辑记录累积偏移量既快又准。M3 之前文件不会被编辑器改动，但"外部修改 + 索引未更新"的场景在 M2 就会出现。
- 精确度标记一旦漏标，`UX_SPEC` §2.2 的"近似结果永远要标明"就破了。宁可把拿不准的标成近似，也不要把近似的标成精确。
- 路由 100 µs 的预算很紧。版本比对不要每次都去算文件哈希——[[idx-life]] 应当缓存"文件 → 索引版本"的映射，本 issue 只做查表比对。
- 本 issue 的前置依赖（[[buffer]]、[[idx-life]]、[[l1]]）全部合并后才能真正跑通，但路由逻辑本身可以先用构造的假索引 + 假缓冲区做单元测试。建议先把这层测试建起来，不要等依赖齐了才开始写。
