## 背景

M0 原计划整理"人工整理的 200 个典型用例测试集"，**没有做完**。报告里只有机器指标：未解析名称占比（中型 0.035% / 大型 0.062%）、光标位置 → 符号查找 0/20,000 错误。这些数字能证明项目模型构造正确、绑定成功，但**不能替代按场景的人工验收**（`M0_LANG_SPIKE_REPORT` §1 的说明块原话），也看不出"`var` 推断的跳转到底对不对"。该报告的"下一步"第 4 项把这件事明确排在 M2 之前。

`LANGUAGE_INTELLIGENCE` §6 的验证计划同样要求："人工整理约 200 个典型用例（var、扩展方法、重载、泛型、继承、Unity API），精确层 100% 正确"。

本 issue 做这个测试集和它的运行器。它是 [[l1]]、[[router]]、[[nav-ui]]、[[integ-m2]] 的共同验收依据，所以**要先于它们可用**。它不依赖 [[contracts]]：直接写在现有的 `crates/rove-lang-cs` 查询 API 上（`CsIndex::goto_definition` / `find_references` 那一层），先跑起来再说。

## 目标

### 1. 200 个用例

在两个本地测试项目中**各整理 100 个**（`ROVE_TEST_UNITY_MEDIUM` / `ROVE_TEST_UNITY_LARGE`）。每个用例包含：文件相对路径、行列位置、期望的定义位置、期望的引用数量（或引用列表的哈希）、场景分类、以及一句话说明为什么选这个点。

### 2. 覆盖的场景分类

每类至少 5 个：

`var` 推断、链式调用、方法重载、扩展方法（含 LINQ 与自定义扩展）、泛型（**含 `GetComponent<T>()`**）、继承与重写（`base.`、`override`）、接口实现、`partial`、Lambda / LINQ、`#if UNITY_EDITOR`（条件编译的两侧都要有用例）、Unity API 等外部符号、局部变量与参数、事件 / 委托、运算符重载、索引器、类型引用。

"类型引用"这一类是 [[l1]] 的验收依据（它要求该类准确率 ≥ 95%），所以这一类要单独标注得足够清楚，能独立统计。

### 3. 用例文件格式

`tests/nav-cases/*.toml`。**只存相对路径与行列，并附上该行的代码文本作为锚点**——测试项目是真实项目，代码会变。运行器先按行列找，文本对不上时在附近若干行内按锚点文本重新定位；定位成功就用新位置，失败就把用例标为"过期"。

用例里不要写绝对路径，也不要写索引文件的内部编号。

### 4. 运行器 `cargo run -p rove-lang-cs --example nav_check`

读取用例，调用 `rove-lang-cs` 的查询接口，输出：

- 每个分类的准确率（通过 / 失败 / 过期）；
- 失败用例的详情：期望什么、实际得到什么；
- 一份机器可读的结果文件，便于前后两次运行对比。

运行器做成 `rove-lang-cs` 的一个 example（与 M0 的 `cs_index_bench` 同样的做法），**不使用 `xtask`**：`xtask` 由 [[perf]] 创建，两者互不依赖，放在 example 里可以避免抢同一个文件。[[perf]] 合并后，如果需要，可以由它再包一层 `cargo xtask nav-check` 的别名。

### 5. 本地运行，不进 CI

两个测试项目都是本地真实项目，不在 CI 中（`ci` 的测试项目环境变量约定）。所以 `nav_check` 只在本地跑：环境变量未设置时**跳过并明确说明原因**，不算失败。用法写进 `AGENTS.md`。

### 6. 适配层

格式变了（[[idx-format]] 的 v2）、查询接口变了（[[contracts]] + [[router]]）时，**只需要改一个地方**。把"用例 → 查询调用 → 结果归一化"收进一个适配层模块，用例文件和统计逻辑都不感知底层。

在 PR 中写明迁移路径：[[router]] 合并后，适配层改为调用 [[contracts]] 的 C# 导航查询接口，并额外断言**精确度标记**（精确 / 近似 / 语法）符合预期——届时同一套用例既验准确率，也验精确度标记是否正确。

### 7. 基线报告

用**当前的 v1 索引**跑一份基线报告（本 issue 只要求基线；“精确层 100% 通过”是 [[integ-m2]] 的验收门槛），连同失败用例的逐条原因一起提交。不要求全部通过——这份基线正是后续几个 issue 的改进依据。

## 不包含

- 修任何导航问题。本 issue 只负责"量出来"，修是 [[idx-format]]、[[idx-meta]]、[[l1]]、[[router]] 的事。
- 界面层的验收（[[nav-ui]]、[[peek]]、[[meta-ui]] 各自在 UI 中抽查，[[integ-m2]] 做端到端）。
- 机器指标（未解析名称占比）：那是索引进程 `--report` 的产出，不在本 issue。
- 性能基准：响应时间由 [[perf]] 的基准与 `cs_index_bench` 负责，`nav_check` 只看对不对。

## 验收标准

- [ ] **200 个用例**，两个项目各 100 个，覆盖上述全部分类且**每类至少 5 个**
- [ ] 用例为 TOML，只含相对路径 + 行列 + 锚点文本 + 期望结果 + 分类；没有绝对路径
- [ ] 锚点重定位有测试：人为在用例文件上方插入几行后，运行器仍能定位到正确的位置
- [ ] 锚点失效时标为"过期"，计入统计但不计为失败
- [ ] `cargo run -p rove-lang-cs --example nav_check` 可运行，输出分类准确率与失败详情，并写出机器可读的结果文件
- [ ] 环境变量 `ROVE_TEST_UNITY_MEDIUM` / `ROVE_TEST_UNITY_LARGE` 未设置时跳过并说明原因，退出码为 0
- [ ] **用 v1 索引跑出一份基线报告**并提交，失败用例逐条记录原因
- [ ] 适配层独立成模块：PR 中指出"格式或接口变化时只需要改哪个文件"
- [ ] `AGENTS.md` 中写明用法与环境变量要求（与 [[ci]] 协调，只追加）

## 风险与提示

- **200 个用例的质量比数量重要**。随便点 200 个标识符，大部分都是简单的局部跳转，测不出任何东西。每一类都要挑"按名称解析一定会错"的点：`LANGUAGE_INTELLIGENCE` §2.1 的那张表就是选点指南（`var p = GetPlayer(); p.Move();`、`a.GetB().GetC().Run()`、`Log(int)` / `Log(string)`、`transform.Reset()` 这类自定义扩展方法）。
- "期望的引用数量"在真实项目里会随代码改动而变。对引用数多的符号，用"数量"做断言很脆；建议只对引用数较少（例如 < 20）的符号断言精确数量，多的符号断言"包含某几个关键位置"。
- 外部符号（Unity API）这一类在 [[idx-meta]] 合并前**必然失败**，因为 v1 索引里根本没有元数据视图。这是预期的，基线报告里标清楚，不要为了让基线好看而把这类用例删掉——它们正是 [[idx-meta]] 的验收依据。
- 用例锚定在真实项目的具体代码上，项目一更新就可能大面积过期。把"如何重新整理过期用例"的步骤写进 `AGENTS.md`，否则半年后这套用例就没人维护了。
- 不要把用例文件做得太聪明（正则匹配、通配期望值）。用例要一眼能看懂"在哪里、期望跳到哪里"，否则失败时没人知道该信用例还是信实现。
