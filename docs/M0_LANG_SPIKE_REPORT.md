# M0 验证报告：C# 预计算语义索引

> 日期：2026-11-09 · 环境：16 核 / 48 GB / Windows 11 · .NET 9 + Roslyn 5.9.0 · Rust 1.97.1
> 代码：`tools/rove-indexer-cs`（索引进程）、`crates/rove-lang-cs`（索引读取与查询）、`crates/rove-lang-cs/examples/cs_index_bench.rs`（基准）

## 结论

**方案可行，建议定案。** 精确度、查询响应、Rove 侧内存三项都大幅优于目标。主要短板集中在**索引进程本身**：首次全量索引耗时、峰值内存、索引体积。这些都属于工程优化问题，不是方案层面的问题，可以在 M2 解决。

## 结果

### 1. 精确度

| 指标 | 中型 | 大型 | 目标 |
|---|---|---|---|
| 未能解析的名称占比 | **0.035%** | **0.062%**（修正 `unmanaged` 关键字误计后） | < 1% |
| 仅有候选（有歧义）的名称 | 68 | 250 | — |
| 光标位置 → 符号查找错误 | 0 / 20,000 | 0 / 20,000 | 0 |

剩余未解析的名称都能对应到项目里真实存在的编译错误或环境问题，例如：
- 中型项目内嵌的 `Packages/com.unity.burst` 只有 19 个编辑器文件，残缺不全，Unity 编译同样会报错；
- `Object` / `UnityObject` 有二义性；
- 部分包代码使用了 Unity 内部 API。

也就是说，**索引结果与编译器一致**。

> 说明：这里还没有完成原计划“人工整理的 200 个典型用例测试集”。上面的数字是机器指标（编译器能否绑定每一个名字），可以证明项目模型构造正确，但不能替代按场景的人工验收。测试集放到 M2 前完成。

### 2. 查询响应（Rove 侧，Rust，mmap 索引，各随机抽样 20,000 次）

| 指标 | 中型 | 大型 | 目标 |
|---|---|---|---|
| 打开索引 | 3.3 ms | 5.7 ms | — |
| 打开后常驻内存增量 | +2.2 MB | +5.2 MB | — |
| 定义跳转 avg / p99 | 2.1 µs / 7.3 µs | 3.5 µs / 12.9 µs | < 16 ms |
| 查找引用 p50 / p99 / max | 5.6 µs / 1.4 ms / 16 ms | 5.7 µs / 3.4 ms / 8.1 ms | < 50 ms |
| 最重的符号（28,671 处引用） | — | 1.95 ms | < 50 ms |
| 单次查找引用的最大结果数 | — | 47,692 条（命名空间等非源码符号；源码符号最多 28,671 条） | — |

查找引用的 max 对应的是 `UnityEngine` 命名空间这类上万处引用的符号；即便如此，耗时也在一帧以内。

> ⚠ **以上是热缓存数据**：索引刚写出，仍在系统文件缓存中。索引不在缓存中时（冷），复测结果如下。注意索引存放在 D 盘，而 D 盘是**机械硬盘**（ST2000DM001）：
>
> | 大型索引，冷缓存，HDD | 数值 |
> |---|---|
> | 打开索引（建立 路径 → 文件 映射，需要读取字符串段） | 3.4 s |
> | 前 200 次定义跳转 p50 / p99 | 9.0 ms / 166 ms |
> | 定义跳转 max | 2.8 s |
>
> 根源是 mmap 缺页变成了 HDD 随机读。设计上因此要求：
> 1. **索引缓存默认放在 `%LOCALAPPDATA%\Rove`**（通常在系统盘或最快的盘上），而不是工作区所在的盘。
> 2. **项目打开时后台顺序预读整个索引文件**（顺序读：HDD 约 150 MB/s，SATA SSD 约 500 MB/s，NVMe 更快；300 MB 约需 2 s / 0.6 s / <0.2 s，均为估算）。预读完成前由 L1 快速索引兜底。
> 3. 路径 → 文件的映射改为按路径排序后二分查找，不在打开时遍历整个字符串段。
> 4. 缩小索引体积（见下一步第 2 项），直接减少冷读量。
>
> SSD/NVMe 上的冷缓存数据**尚未测量**（无法可靠清除指定文件的系统缓存），M2 补测。

> 注：基准跑完后进程常驻内存为 115 MB / 350 MB，原因是基准遍历了整个索引，所有页面都被映射进来。这些页面以文件为后备，内存紧张时系统会直接回收。正常使用时只会触达少量页面。

### 3. 同名噪音：为什么必须用语义索引

在大型项目中，“按名称查引用”（纯语法方案）与“语义查引用”的对比：

| 名称 | 同名的不同符号数 | 按名称命中数 | 语义：每个符号平均引用数 | 语义：最多 |
|---|---|---|---|---|
| `Init` | 789 | 1,761 | 2.2 | 54 |
| `Update` | 636 | 1,366 | 2.1 | 113 |
| `Dispose` | 1,185 | 4,008 | 3.4 | 532 |
| `Get` | 197 | 7,357 | 37.3 | 4,404 |
| `Value` | 250 | 6,541 | 26.2 | 3,954 |

举例：查找某个 `Init` 的引用，按名称搜索会返回 1,761 条，其中只有大约 2 条是你要找的。这从数据上证实了纯语法索引无法承担“查找引用”。

### 4. 索引进程（建索引的开销）

| 指标 | 中型 | 大型 | 目标 |
|---|---|---|---|
| 首次全量索引总耗时 | 44 s | 157 s（冷缓存）/ 118 s（热缓存） | < 90 s（大型） |
| ├ 解析 csproj + 与磁盘对齐 | 0.7 s | 4.5 s | |
| ├ 语法解析（读文件） | 3.6 s | 56 s（冷）/ 8.9 s（热） | |
| ├ 构造编译 | 0.4 s | 13.5 s | |
| ├ 绑定 + 收集 | 35 s | 72 s | |
| └ 写索引 | 4.4 s | 11.7 s | |
| 峰值内存（进程结束即释放） | 2.2 GB | 5.5 GB | < 3 GB |
| 索引文件大小 | 94 MB | 303 MB | < 200 MB |
| 开启 Source Generators 的额外耗时 | +8.8 s | 约 +1 s | |
| Source Generators 生成的文件数 | 0 | 0 | |

- 大型项目首次语法解析耗时 56 s，热缓存复测降到 8.9 s，确认是 E 盘冷读取 I/O 造成的。冷启动场景下要考虑读文件的并发度，以及对 HDD 的友好性。
- 测量期间，另一个 UI 验证任务在同机并行执行 cargo 编译，绑定阶段的耗时存在噪声（同样的中型项目，多次运行在 29–42 s 之间波动）。

## 验证中发现的真实问题（都已在原型里处理）

1. **csproj 过期**。Unity 只在编辑器刷新时重新生成 csproj。中型项目里有 242 个新 `.cs` 文件不在任何 csproj 中，另有 165 个已列出的文件已被删除；验证期间，这个项目在 1 小时内改动了 790 个文件。
   → 索引进程按 Unity 自己的规则与磁盘对齐：就近的 `.asmdef`/`.asmref` → `Editor` 目录 → `Assembly-CSharp(-firstpass)(-Editor)`。修正后，`Football.Core` 的未解析名称从 765 降到 0。
2. **预处理宏必须在解析时生效**。`#if UNITY_EDITOR` 在解析阶段求值，必须用文件所属项目的宏来解析，否则 Fbx 等包的全部 API 都会被当成禁用代码。修正后，中型项目的未解析率从 0.19% 降到 0.035%。
3. **文件被占用**。Unity 编辑器或杀毒软件可能独占打开文件，必须以共享模式读取并重试。
4. **Source Generators**：所有 csproj 都挂了 Unity 的生成器，大型项目还有 37 个项目挂了 Entities 生成器。但两个项目开启后都生成了 0 个文件，未解析率没有变化。**建议默认关闭。** 注意：还没有确认这些生成器是否真的被成功加载（也可能是项目里根本没有触发生成的代码）。需要找一个使用了 `ISystem` / `[GeneratePropertyBag]` 的项目复核。

## 对设计文档的修正

- 项目模型：“直接解析 csproj”要改为“**csproj 提供引用和宏，文件列表以磁盘 + asmdef 规则为准**”。
- 增量更新：项目文件在频繁变化（AI 工具批量改动），增量更新的优先级比预期更高，M2 必须做。
- 外部符号：约 30% 的跳转目标是 DLL 中的符号（UnityEngine、BCL），源码中没有定义。需要“元数据视图”（签名 + XML 文档注释），否则跳转会落空。M2 必须做。

## 下一步（M2 前）

1. 索引进程性能：把读文件和解析流水线化；拆分绑定的并行粒度；写索引改为流式写入，避免在内存中积累整个列表。目标：大型项目 < 90 s、峰值 < 3 GB。
2. 索引体积：局部符号改用二进制键，出现位置改用变长编码。目标：大型项目 < 200 MB。
3. 增量：单文件重绑 + 覆盖层（overlay）索引，测量单文件更新耗时（目标 < 300 ms）。
4. 人工测试集：在两个项目中各选 100 个场景（var、扩展方法、重载、泛型、继承、partial、Unity API），逐一验证。
5. 元数据视图：外部符号的签名和文档注释。

## 复现

```bash
cd tools/rove-indexer-cs && dotnet build -c Release
tools/rove-indexer-cs/bin/Release/net9.0/rove-indexer-cs.exe <unity-project> out/x.idx --report out/x.json [--generators] [--diag <AssemblyName>]
cargo run --release -p rove-lang-cs --example cs_index_bench -- out/x.idx 20000
```
