# R49 热退出与崩溃恢复（D8：从 M4 提前，避免 M3 交付后意外退出丢失修改）

| 里程碑 | 难度 | 领域 | 并行批次 | 前置依赖 | 被依赖 |
|---|---|---|---|---|---|
| M3 轻编辑 | 2 中等 | core | 第 6 批 | R48（保存与外部修改）、R16（工作台） | R50（【集成验收】M3）、R76（自动更新） |

> 认领前请阅读 `AGENTS.md`、`docs/ARCHITECTURE.md`（R01 完成后）与 `docs/issues/README.md`。前置依赖全部合并后才能开工。

## 背景

热退出是 VS Code 用户默认会依赖的行为（`FEATURES.md` §6：照搬 / P1）：关窗口时有未保存的修改不会被追问，下次打开原样回来。`UX_SPEC.md` §6.4 还给了一条明确要求——**Rove 上次意外退出时，下次启动恢复热退出的备份，并在状态栏提示“已恢复上次未保存的修改”；崩溃日志只保存在本地，不上传**。

R48（保存与外部修改） 已经建好了脏状态跟踪、关闭未保存文件的模态框，以及原子写入路径，并且在第 3 节留好了“`files.hotExit` 生效时跳过模态框”的开关点。本 issue 把那个开关接上，并补上备份、恢复与崩溃恢复。

这是一个“不出事就完全看不见”的功能，所以验收必须包含**真的把进程杀掉**这一步，而不是只测正常退出。

必读：`FEATURES.md` §6（热退出一行）、§10（遥测与运营：**不做**）、§13（`rove.*` 命名空间与状态目录约定），`UX_SPEC.md` §6.1（第 1 级反馈：状态栏临时消息）、§6.4 最后一行，`SETTINGS.md`（`files.hotExit`、`files.restoreUndoStack`）。

## 目标

### 1. `files.hotExit` 语义

逐一实现三种取值（默认 `onExit`）：

| 取值 | 行为 |
|---|---|
| `off` | 不备份；关闭有未保存修改的标签 / 窗口时按 R48（保存与外部修改） 的模态框询问 |
| `onExit` | **退出应用**时备份未保存的修改并跳过询问；关闭单个窗口（还有其他窗口在）时仍然询问 |
| `onExitAndWindowClose` | 关闭任意窗口时都备份并跳过询问 |

Rove 是“一个窗口一个文件夹”（`FEATURES.md` §6：不做多根工作区），所以“窗口”与“工作区”一一对应，备份按窗口分组。

### 2. 备份

- 位置：`%LOCALAPPDATA%\Rove\backups\<工作区路径哈希>\`，与 R36（索引生命周期与状态） 的 `%LOCALAPPDATA%\Rove\index\<项目路径哈希>\` 采用同一套哈希与目录约定。**本 issue 不新增 `rove.*` 设置项**；确实需要可配置时，按 `SETTINGS.md` §4 的格式单独提 PR 加。
- 内容：每个脏文档一份——原始路径、打开时识别出的编码与 BOM、主换行符与“是否混合”、文档版本、以及缓冲内容。恢复后必须能原样保存（编码往返零差异的责任仍在 R48（保存与外部修改），本 issue 负责不丢这些元信息）。
- 写入方式复用 R48（保存与外部修改） 的原子写入（临时文件 + 替换），避免崩溃时留下半截备份。
- 时机：按编辑去抖**持续备份**（不只在退出时写），否则进程被强杀时什么都没有——这正是 `UX_SPEC.md` §6.4 要覆盖的场景。去抖间隔与 I/O 量要在 PR 中给出数据。
- 清理：文档被保存或关闭后删除对应备份；启动恢复完成后清理已消费的备份；工作区目录已不存在时清理整组。

### 3. 恢复

- 启动时发现本工作区有备份：恢复这些文档（重新打开标签、内容取自备份、标记为脏），**保持它们原来的标签顺序与活动标签**。
- 上次是**正常退出**（有干净的退出标记）：静默恢复，不提示。
- 上次是**意外退出**（没有退出标记）：恢复后按 `UX_SPEC.md` §6.4 在状态栏提示“已恢复上次未保存的修改”（第 1 级反馈，3 秒后消失，走 R16（工作台） 的反馈接口），**不弹通知、不弹模态框**。
- 备份对应的磁盘文件在此期间被外部改过：交给 R48（保存与外部修改） 的保存冲突路径处理，不自己再造一套提示。
- 磁盘文件已被删除：恢复为“已删除”状态的标签（与 R48（保存与外部修改） 第 4 节一致），内容保留。
- `files.restoreUndoStack`（默认 true）：恢复文档时一并恢复撤销栈。**这一项归本 issue**——它是“跨会话保留编辑器状态”的一部分，与备份用同一份持久化。撤销栈过大时按上限截断并在 PR 中说明上限取值。

### 4. 崩溃恢复与崩溃日志

- 退出标记：正常退出时写入，启动时读到就按“正常退出”处理，读不到就按“意外退出”处理；启动后立刻清除标记，使本次运行默认处于“未正常退出”状态。
- 崩溃日志：panic 与致命错误写入 `%LOCALAPPDATA%\Rove\logs\`（带时间戳、保留最近 N 份），内容只含堆栈与环境信息。**只保存在本地，不上传，不发起任何网络请求**（`FEATURES.md` §10 遥测不做）。日志中不得包含文件内容与路径之外的用户数据。
- 连续崩溃时不要反复尝试恢复同一份有问题的备份：记录恢复尝试次数，第二次仍失败就把该备份移到 `backups-failed\` 并在状态栏提示一次。

### 5. 登记与替换

新增设置项、界面字符串通过 R01（【接口先行 A1】架构与接口契约） 的登记机制加入，不得写死；状态栏提示走 R16（工作台） 的反馈接口。R02（【接口先行 A2】行走骨架） 中没有本 issue 对应的 `SKELETON(...)` 标记，只在 `docs/ARCHITECTURE.md` 中新增 / 更新自己的一行。不得在本 PR 中修改 R01（【接口先行 A1】架构与接口契约） 与 R48（保存与外部修改） 的接口（需要扩展时走契约变更流程单独提 PR）。

## 不包含

- 保存本身、原子写入、编码回写、外部修改与保存冲突、关闭未保存文件的模态框（R48（保存与外部修改））；本 issue 只决定“什么时候跳过那个模态框”。
- 未命名文件（`workbench.action.files.newUntitledFile`，归 R62（资源管理器文件操作））的备份：R62（资源管理器文件操作） 合并前没有未命名文档可备份，接口按“有路径的文档”设计并留出扩展点。
- 本地历史（localHistory，P2）、与已保存版本比较（P2）——它们解决的是“被外部工具改坏”，不是“没来得及保存”。
- 布局与标签的持久化本身（R16（工作台） 的布局持久化、R17（编辑器组与标签） 的标签状态）；本 issue 只保证被恢复的文档落在正确的标签位置上。
- 崩溃上报、遥测、自动更新（`FEATURES.md` §10：不做）。
- 索引进程的崩溃处理（R36（索引生命周期与状态），按 `UX_SPEC.md` §2.1 的“失败”状态）。

## 验收标准

- [ ] `files.hotExit` 三种取值各有用例：`off` 时询问、`onExit` 时退出应用不询问但关单窗口询问、`onExitAndWindowClose` 时都不询问
- [ ] **强杀进程**（`Stop-Process -Force`）后重启：未保存的修改全部回来，内容逐字节一致，标签顺序与活动标签保持，状态栏出现“已恢复上次未保存的修改”
- [ ] 正常退出后重启：内容同样回来，但**不出现**那条提示
- [ ] 恢复后直接保存：GBK + CRLF、UTF-8 带 BOM、混合换行符三类文件各一例，除改动处外**字节完全一致**（与 R50（【集成验收】M3） 的口径一致）
- [ ] 备份期间磁盘文件被外部修改 / 被删除两种情况各有用例，分别落到 R48（保存与外部修改） 的冲突路径与“已删除”标签
- [ ] `files.restoreUndoStack` 为 true 时恢复后可继续 `Ctrl+Z` 回到更早的状态；为 false 时撤销栈为空；撤销栈超限时按上限截断且不报错
- [ ] 备份清理：保存后、关闭后、恢复消费后对应备份文件消失；工作区被删除后整组备份被清理
- [ ] 连续两次恢复失败的备份被移入 `backups-failed\`，不进入无限恢复循环
- [ ] 崩溃日志写入本地且**没有任何网络访问**（用网络访问断言覆盖，与 R31（【集成验收】M1） 的“全程无运行时网络访问”口径一致）
- [ ] 持续备份的 I/O 开销：连续输入 1 分钟时的写入次数与字节数（附数据），不影响按键到上屏的 8 ms 预算
- [ ] 新增的设置项与界面字符串都经由登记机制，无硬编码
- [ ] R02（【接口先行 A2】行走骨架） 的端到端测试仍然通过；新增“编辑 → 强制退出 → 重启恢复”的集成测试

## 风险与提示

- **“只在退出时备份”是这个功能最常见的错误实现**。那样做正常关闭能过，崩溃恢复一条都过不了，而 `UX_SPEC.md` §6.4 要的正是崩溃这一条。持续备份 + 去抖是唯一能同时满足两者的做法。
- 备份里丢掉编码 / BOM / 混合换行符信息，恢复后保存就会产生整文件差异——那等于绕过了 M3 花很大力气守住的“零差异”。备份格式里这三项是必填，不是可选。
- 退出标记的写入时机要小心：写得太早（启动时写“正常”）等于永远检测不到崩溃；正确做法是启动时清除、正常退出时写入。
- 测试一定要真的 `Stop-Process -Force`，不要用“模拟崩溃”的内部开关替代——内部开关走的还是正常的析构路径。
- 备份目录可能被杀毒软件锁住或被用户清理工具删掉。读不到备份时按“没有备份”处理，静默继续启动，不要因为恢复失败而让 Rove 打不开。
