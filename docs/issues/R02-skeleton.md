# R02 【接口先行 A2】行走骨架：用最简实现打通“打开文件夹 → 文件树 → 点击文件 → 带高亮显示”的完整链路

| 里程碑 | 难度 | 领域 | 并行批次 | 前置依赖 | 被依赖 |
|---|---|---|---|---|---|
| M1 只读阅读器 | 3 困难 | ui | 第 2 批 | R01（【接口先行 A1】架构与接口契约） | R07（文本缓冲）、R09（tree-sitter 集成）、R10（主题引擎）、R14（键位与命令层）、R15（工作区）、R16（工作台）、R17（编辑器组与标签）、R18（通用列表、树与快速输入组件）、R19（代码视图 Element） |

> 认领前请阅读 `AGENTS.md`、`docs/ARCHITECTURE.md`（R01 完成后）与 `docs/issues/README.md`。前置依赖全部合并后才能开工。

## 背景

R01（【接口先行 A1】架构与接口契约） 定义了接口，但接口能否真正组合起来，只有跑通一条完整链路才能确认。本 issue 用**最简实现**打通 Rove 最核心的一条链路，让后续 issue 都在一个“能运行的程序”上替换各自的部分，而不是各自从零开始、最后再拼。

这也是第一次在 GPUI 中运行 Rove 的界面。可以参考 M0 的原型 `spikes/ui-gpui/`。

## 目标

### 1. 打通的链路

```
rove.exe <文件夹路径>
  → 打开窗口（最简工作台：左侧文件树，右侧编辑区，底部状态栏）
  → 扫描文件夹，显示文件树
  → 点击一个文件
  → 通过“打开文档服务”打开它
  → 在编辑区显示文本，并带有语法高亮（至少支持 C#）
  → 状态栏显示文件名、行数、编码
```

### 2. 每个环节的最简实现

所有最简实现都必须**通过 R01（【接口先行 A1】架构与接口契约） 定义的接口**接入，不允许绕过接口直接调用。

| 环节 | 最简实现 | 之后由谁替换为正式实现 |
|---|---|---|
| 工作区扫描 | 递归列出文件，只排除 `.git`、`Library`、`Temp`，不监听变化 | R15（工作区） |
| 文件树 | 一个简单的可展开列表 | R23（资源管理器）、R18（通用列表、树与快速输入组件） |
| 打开文档服务 | 单个编辑区，打开新文件时直接替换 | R17（编辑器组与标签） |
| 文本缓冲 | 按 UTF-8 读取整个文件 | R07（文本缓冲） |
| 语法高亮 | 只接入 tree-sitter C#，用少量查询规则产生 scope | R09（tree-sitter 集成） |
| 主题 | 硬编码 Dark 2026（VS Code 当前默认主题）中最常用的几条 token 颜色和界面颜色，通过颜色键登记表登记 | R10（主题引擎） |
| 代码视图 | 只绘制可见行，用最简单的滚动方式；可以直接沿用 M0 原型的写法 | R19（代码视图 Element）、R20（代码视图） |
| 状态栏 | 固定显示三项信息 | R16（工作台）、R27（状态栏条目） |
| 命令与键位 | 登记 2–3 个命令（例如 `workbench.action.quickOpen` 先显示“未实现”的提示），用硬编码的键位触发 | R14（键位与命令层） |
| 界面字符串 | 所有可见文字都通过字符串表获取 | — |

### 3. 标记“待替换”

每一处最简实现都在代码中加上统一的标记注释（例如 `// SKELETON(workspace): …`，括号里写负责替换它的 issue 的键名）。**一个标记只对应一个 issue**：同一处由多个 issue 分别替换时（例如状态栏由 R16（工作台） 提供容器、由 R27（状态栏条目） 提供条目），就并列打多个标记，每个 issue 只删除自己的那个。上面表格中列出的每一个负责 issue 都必须至少有一个标记。并在 `docs/ARCHITECTURE.md` 中维护一张“最简实现 → 负责替换的 issue”的对照表。各 issue 完成后，删除对应的标记并更新这张表。这样随时都能看出哪些部分还是临时实现。

### 4. 端到端测试

在 GPUI 的测试环境（`TestAppContext`）中写一个端到端测试：打开测试用的文件夹 → 选中一个 `.cs` 文件 → 断言文档已经打开、编辑区显示了第一行、第一行中的关键字被赋予了预期的 scope 和颜色。**后续每个 issue 都必须保证这个测试持续通过**；集成验收 issue 会在它的基础上补充更多场景。

## 不包含

- 任何性能优化（虚拟化以外的部分）、超大文件、编码识别、设置文件、多标签、搜索等。
- 视觉打磨。

## 验收标准

- [ ] `cargo run -p rove-app -- <文件夹>` 可以打开中型 Unity 测试项目（`ROVE_TEST_UNITY_MEDIUM`），浏览文件树，打开 `.cs` 文件并看到高亮
- [ ] 链路中的每一个环节都通过 R01（【接口先行 A1】架构与接口契约） 的接口接入；PR 描述中逐项说明
- [ ] 所有最简实现都带有 `SKELETON(...)` 标记，`ARCHITECTURE.md` 中的对照表与代码一致
- [ ] 端到端测试通过，并已加入 `cargo test --workspace`
- [ ] 日志中记录从进程启动到首帧的时间（供 R04（性能基准与预算守护） 采集；这里不要求达标）
- [ ] 如果发现 R01（【接口先行 A1】架构与接口契约） 的接口有缺陷，按契约变更流程单独提 PR 修正，不在本 PR 中顺手修改

## 风险与提示

- 本 issue 的价值在于**验证接口能否组合**，不是做出好用的功能。遇到接口不顺手的地方，记录下来并修正契约，比在骨架里绕过去更重要。
- 保持最简：任何一处“顺便做好一点”，都可能和负责正式实现的 issue 冲突。
