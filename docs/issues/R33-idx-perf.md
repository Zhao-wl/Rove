# R33 索引进程性能优化（大型项目 < 90 s、峰值 < 3 GB）

| 里程碑 | 难度 | 领域 | 并行批次 | 前置依赖 | 被依赖 |
|---|---|---|---|---|---|
| M2 C# 导航 | 4 专家 | indexer | 第 2 批 | R32（C# 索引格式 v2） | R34（外部符号元数据视图的生成）、R35（增量索引） |

> 认领前请阅读 `AGENTS.md`、`docs/ARCHITECTURE.md`（R01 完成后）与 `docs/issues/README.md`。前置依赖全部合并后才能开工。

## 背景

M0 的结论是"方案可行，短板集中在索引进程本身"（`M0_LANG_SPIKE_REPORT` 的结论一节）。实测与目标的差距：

| 指标 | 中型 | 大型（实测） | 目标 |
|---|---|---|---|
| 全量索引总耗时 | 44 s | 157 s（冷）/ 118 s（热） | < 90 s |
| 峰值内存 | 2.2 GB | **5.5 GB** | < 3 GB |

各阶段耗时（大型项目）：解析 csproj 与磁盘对齐 4.5 s、语法解析 **56 s（冷）/ 8.9 s（热）**、构造编译 13.5 s、**绑定 + 收集 72 s**、写索引 11.7 s。可以看出三个着力点：绑定阶段的 CPU、冷读取的 I/O、以及"把所有结果先攒在内存里再写"的内存峰值。

本 issue 只做索引进程（`tools/rove-indexer-cs/`）的工程优化，**不改索引格式**——格式 v2 由 R32（C# 索引格式 v2） 先行完成，本 issue 在它之上改写入路径。

## 目标

### 1. 先剖析，再动手

用 `dotnet-trace` / `dotnet-counters` 做一次完整剖析，至少回答三个问题：

- 绑定阶段（72 s）的时间花在哪里：`GetSymbolInfo` 本身、语义模型的首次构建、还是我们自己的遍历与字典操作；
- 5.5 GB 内存里**各占多少**：语法树、语义模型缓存、`ConcurrentDictionary<string, List<Occ>>` 里积累的出现位置、字符串表；
- GC 的代际分布与大对象堆的占用。

剖析结论要先写下来，优化方向以数据为准，不要凭下面的清单硬套。

### 2. 可能的优化方向（按剖析结果取舍）

- **按项目依赖拓扑分批绑定**：大型项目有 242 个 csproj。按依赖拓扑排序分批，一批绑定完就释放这一批的 `Compilation` 与语义模型，不要 242 个编译同时活着。这是降内存峰值最直接的一刀。
- **流式写入**：出现位置边收集边按文件写入临时段，最后归并，不在内存中积累全部列表（M0 的"写索引 11.7 s"里有相当一部分是在搬运这些列表）。
- **读取与解析流水线化，并发度可控**：冷读取时语法解析 56 s、热缓存 8.9 s，差的全是 I/O。读文件和建语法树要能重叠起来，同时**并发度要有上限并对机械硬盘友好**（过高的并发度在 HDD 上会把顺序读打散成随机读，反而更慢）。并发度做成参数，在 HDD 与 SSD 上各测一组。
- **减少 `GetSymbolInfo` 调用**：跳过不可能引用符号的语法节点（关键字、字面量、纯标点、注释内的标识符）。
- 字符串驻留，减少重复分配。

### 3. 冷启动 I/O

单独测量并报告冷读取路径的改进幅度（清掉系统缓存或换一台机器）。冷缓存下的总耗时也要给出数字，哪怕达不到 90 s，也要说明差距和原因。

### 4. 源生成器：确认是否真的被加载，并定默认值

M0 中两个项目的所有 csproj 都挂了 Unity 的生成器（大型项目另有 37 个项目挂了 Entities 生成器），开启后**生成了 0 个文件**，未解析率没有变化，耗时却多了 8.8 s / 1 s。但 M0 **没有确认这些生成器是否真的被成功加载**（也可能项目里根本没有触发生成的代码）。

本 issue 要查清楚：找一个使用了 `ISystem` / `[GeneratePropertyBag]` 的项目（或自建最小复现工程）复核，确认生成器确实被加载并执行。然后给出结论：`--generators` 的默认值是什么、什么情况下建议用户打开。结论写进 `docs/LANGUAGE_INTELLIGENCE.md` §3.3。

### 5. 报告

沿用现有的 `--report`，输出各阶段耗时、峰值内存、文件数、符号数、出现位置数、未解析名称占比。优化前后的数据补进 `docs/M0_LANG_SPIKE_REPORT.md`（或另写一份 M2 的性能报告并在该文档中链接）。

## 不包含

- 索引格式的任何修改（R32（C# 索引格式 v2））。
- 元数据视图的生成（R34（外部符号元数据视图的生成））。
- 常驻模式与增量更新（R35（增量索引））；本 issue 只优化全量索引这一条路径。
- Rove 侧的查询性能（M0 实测已远优于目标，不是本 issue 的问题）。
- 打包与分发（R43（索引组件打包与版本握手））。

## 验收标准

- [ ] 大型项目（`ROVE_TEST_UNITY_LARGE`）全量索引：热缓存 < 90 s，峰值内存 < 3 GB
- [ ] 冷缓存下的总耗时与峰值内存也有数字，并说明与热缓存的差距来自哪个阶段
- [ ] 中型项目（`ROVE_TEST_UNITY_MEDIUM`）同步给出优化前后对比，不得退化
- [ ] **精确度不退化**：未解析名称占比与 M0 一致（中型 0.035%、大型 0.062% 上下），"仅有候选"的名称数量也在同一量级（中型 68、大型 250）
- [ ] "光标位置 → 符号查找"抽样 20,000 次仍然 0 错误
- [ ] 每项性能数字都是**同一台机器上至少 3 次运行的中位数**，并记录运行期间机器是否有其他负载
- [ ] 读取并发度在 HDD 与 SSD 上各有一组数据，默认值的选择有依据
- [ ] 源生成器是否被成功加载有明确结论与复核方法，默认值已定并写入文档
- [ ] 剖析结论与优化前后的数据已写入报告文档
- [ ] 索引进程运行期间不发起任何网络请求（NuGet 还原在构建期完成，运行期为零）

## 风险与提示

- **测量噪声是这个 issue 最大的坑**。M0 测量时同机并行跑着 cargo 编译，同一个中型项目的绑定阶段在 29–42 s 之间波动。定一个固定的测量流程（关闭其他负载、固定电源策略、至少 3 次取中位数），写进 PR，之后所有人都照这个流程复现。
- "绑定 72 s"听起来像是 Roslyn 的开销，但分批绑定会**改变并行结构**，很容易在降内存的同时把耗时推高。两个指标要一起看，不要为了 3 GB 把 90 s 丢了。
- 任何会改变绑定行为的优化（跳过节点、改并行粒度、复用语义模型）都有"少收集了一些引用"的风险。精确度指标是硬门槛，每轮优化后都要重跑，不要留到最后。
- **索引进程的文件按 R32（C# 索引格式 v2） → R33（索引进程性能优化） → R34（外部符号元数据视图的生成） / R35（增量索引） 的顺序串行修改**。本 issue 是第二棒：等 R32（C# 索引格式 v2） 合并后再开工，自己合并后 R34（外部符号元数据视图的生成） 与 R35（增量索引） 才动手。
- 流式写入和 R35（增量索引） 的覆盖层会动同一段写入代码。本 issue 在设计流式写入时，把"追加一个段"的路径留出来，可以省掉后面一次返工。
