## 背景

L2 语义索引很准，但大型项目的首次全量索引要 90 s 以上；索引失效、组件未安装、文件刚被改过的时候，它也用不上。`LANGUAGE_INTELLIGENCE` §3.1 的三层结构里，**L1 快速声明索引**就是填这个空档的：打开项目后几秒内就有可用的导航，并在 L2 不可用时作为回退（§3.4）。

L1 用 tree-sitter 在 Rust 侧实现，**复用 R09（tree-sitter 集成） 已经集成的 C# grammar**，只扫声明、不做类型推断。它能承担的能力是明确的（§2.1 的表已经把天花板写清楚了）：工作区符号搜索、按"命名空间 + 类型名"的类型跳转、以及按名称给出候选成员——**候选成员一律标记为"近似"**。成员级的精确跳转和查找引用不归它管：M0 实测大型项目里 `Init` 有 789 个同名符号、按名称搜索返回 1,761 条结果而真正相关的只有约 2 条，这是纯语法方案的硬伤。

实现放在 `crates/rove-lang-cs` 的 L1 模块，查询结果通过 R01（【接口先行 A1】架构与接口契约） 定义的 C# 导航查询接口（带精确度标记）对外暴露，由 R38（查询路由与未保存修改的位置映射） 调度；**本 PR 不修改这些接口**。

## 目标

### 1. 并行声明扫描

并行扫描工作区中全部 `.cs` 文件（文件列表与排除规则来自 R15（工作区），不要自己遍历目录），用 tree-sitter 提取：

- 命名空间（含文件级 `namespace X;` 的新写法）；
- 类型：class / struct / interface / enum / record / delegate，含嵌套类型与泛型参数个数；
- 成员：方法、属性、字段、事件、构造函数、索引器、运算符；
- 每个声明的位置（行 + UTF-8 字节列）和容器链。

**`partial` 类型要聚合**：同一个类型分布在多个文件中时，对外是一个符号，但保留全部声明位置（跳转时给出多个候选，这与 R40（C# 导航交互） 的"多个定义时打开速览"一致）。

不做绑定、不做类型推断、不处理 `#if`（条件编译区域内的声明照常收集，由 R38（查询路由与未保存修改的位置映射） 决定要不要用）。

### 2. 持久化与增量更新

结果持久化到 R36（索引生命周期与状态） 定义的缓存目录布局下（与 L2 索引同一个项目目录，不同文件）。再次打开项目时按文件的修改时间或内容哈希做增量更新，只重扫变化的文件。文件事件同样来自 R15（工作区）。

### 3. 查询能力

- **工作区符号模糊搜索**：按符号名模糊匹配，返回带容器与位置的结果。匹配算法复用 R24（快速打开与命令面板） 移植的 VS Code 模糊匹配，不要另写一套打分规则。
- **类型引用解析**：给定一个标识符和它所在的位置，按"当前命名空间 + 文件中的 `using`（含 `using static`、`using X = Y;` 别名）+ 全局 using"解析到类型符号。这是 L1 唯一能做到接近精确的场景。
- **候选成员**：按名称给出同名成员列表，**结果一律标记为"近似"**（R01（【接口先行 A1】架构与接口契约） 的精确度标记中的"近似"一档）。

### 4. 与三层结构的衔接

L1 只负责"给出结果和它的精确度"，什么时候用 L1、什么时候用 L2 由 R38（查询路由与未保存修改的位置映射） 决定。L1 要对外暴露"当前构建进度"和"某个文件是否已扫描"，供 R38（查询路由与未保存修改的位置映射） 和 R36（索引生命周期与状态） 的状态显示使用。

## 不包含

- tree-sitter 与 C# grammar 的集成、`highlights.scm`（R09（tree-sitter 集成））。
- 查询路由、未保存修改的位置映射、L0 的局部变量与参数兜底（R38（查询路由与未保存修改的位置映射））。
- L2 索引的任何部分（R32（C# 索引格式 v2）、R36（索引生命周期与状态））。
- 大纲与文件内符号：那是 R26（大纲） 基于 `rove-syntax` 的文档符号做的，和 L1 是两套数据，**不要互相替代**（但 PR 中要说明两者的关系，避免重复实现）。
- 工作区符号搜索的界面浮层（R59（转到类型定义、工作区符号、侧边引用视图） 的 `Ctrl+T`）。

## 验收标准

- [ ] 大型项目（`ROVE_TEST_UNITY_LARGE`，2.1 万个 `.cs` 文件）**首次构建 < 5 s（热缓存）**；中型项目（`ROVE_TEST_UNITY_MEDIUM`，7,719 个文件）同步给出数字
- [ ] 单文件变更后的**增量更新 < 100 ms**
- [ ] **工作区符号搜索每次按键 < 30 ms**（`LANGUAGE_INTELLIGENCE` §1 的目标；在大型项目上测，含模糊匹配与排序）
- [ ] 在 R39（C# 导航准确率测试集） 的用例集上，**"类型引用"类用例的准确率 ≥ 95%**（与 L2 的结果对比；不达标时逐条记录失败原因）
- [ ] `partial` 类型聚合有测试：分布在 3 个文件中的 `partial class` 对外是一个符号、有 3 个声明位置
- [ ] 嵌套类型、泛型类型（按参数个数区分 `List<T>` 与 `List<T1,T2>` 这类重名）、`record`、文件级 namespace 各有用例
- [ ] `using static` 与 `using X = Y;` 别名在类型解析中生效，各有用例
- [ ] 候选成员的结果全部带"近似"标记，没有任何一条被标成"精确"
- [ ] 持久化与增量：关闭后重新打开项目，不重扫未变化的文件（用扫描计数断言）
- [ ] 常驻内存增量有数字（L1 是一直活着的，不像 L2 可以按需映射）
- [ ] 新增集成测试覆盖"扫描工作区 → 符号搜索 → 类型跳转"；R02（【接口先行 A2】行走骨架） 的端到端测试继续通过
- [ ] `cargo tree -p rove-lang-cs -i gpui` 为空

## 风险与提示

- **目标说明**：`LANGUAGE_INTELLIGENCE` §3.4 的 3 s 是按 1 万个文件定的，大型测试项目是 2.1 万个文件，因此这里按热缓存 < 5 s 验收；冷缓存不设门槛，但必须报告数字。**瓶颈在 I/O 不在解析**。M0 实测大型项目冷读取时光语法解析就要 56 s（热缓存 8.9 s），虽然 L1 的查询比索引进程简单得多，但读文件的量是一样的。并发度要可控，并在 HDD 与 SSD 上各测一组——冷场景下 L1 需要多久要如实报告；在此期间导航仍可由 L0 兜底。
- 不要让 L1 悄悄越界。tree-sitter 能看出 `p.Move()` 里有个 `Move`，但看不出 `p` 是什么类型。一旦开始"猜类型"，就会产出看起来精确实际错误的结果，这比明确标注"近似"糟糕得多。§2.1 的那张表就是边界，照着它做。
- 常驻内存是 L1 的隐形成本。2.1 万个文件、几十万个声明，如果每个声明都存完整字符串，内存会很可观。考虑字符串驻留或共享的名称表。
- R39（C# 导航准确率测试集） 是本 issue 的验收依据之一，但它独立于 R01（【接口先行 A1】架构与接口契约） 先行开发（跑的是当前的 `rove-lang-cs` API）。开工前确认它的用例集和适配层已经可用，否则"≥ 95%"无从验证。
