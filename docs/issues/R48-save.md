| 里程碑 | 难度 | 领域 | 并行批次 | 前置依赖 | 被依赖 |
|---|---|---|---|---|---|
| M3 轻编辑 | 3 困难 | core | 第 5 批 | R45（编辑核心模型）、R15（工作区）、R16（工作台）、R09（tree-sitter 集成） | R49（热退出与崩溃恢复）、R50（【集成验收】M3）、R51（多光标与行操作）、R61（全局替换） |

> 认领前请阅读 `AGENTS.md`、`docs/ARCHITECTURE.md`（R01 完成后）与 `docs/issues/README.md`。前置依赖全部合并后才能开工。

## 背景

Rove 的卖点之一是“看一眼、改一行、保存，版本控制里只有那一行的差异”。做到这一点要求保存路径上**什么都不顺手改**：编码、BOM、混合换行符、文件末尾有没有换行，全部按打开时的样子写回（`UX_SPEC.md` §3.5、§3.6）。VS Code 在混合换行符上会静默统一，这是 Rove 明确要偏离的地方。

另一半是 Windows 的现实：Unity 正在导入时文件被占用、`.meta` 带只读属性、外部脚本在后台连续改写同一个文件。`UX_SPEC.md` §6.4 为这些情况逐条规定了处理方式，而且特意写明**不提供“以管理员身份保存”**。

本 issue 的写入实现放在 `rove-buffer`（在 R45（编辑核心模型） 的事务之上），界面反馈经 R16（工作台） 的五级反馈接口，文件事件来自 R15（工作区） 的监听。可以参考被取代的草稿 `out/issues-superseded/05-edit-docview.md` 的「保存与外部修改重载」一节。

必读：`UX_SPEC.md` §3.5、§3.6、§6.1（**模态框只用于不立即处理就会丢数据的情况**）、§6.4，`FEATURES.md` §6（文件监听与自动重新加载 P0、热退出 P1）、§13，`docs/compat/KEYBINDINGS.md`（文件一节 + §7 附录中“P0 · 文件”），`SETTINGS.md`（`files.*`），`THEME_COLORS.md`（Notification colors、Status Bar colors）。

## 目标

### 1. 保存：原样写回

- 保持**编码**（含候选编码识别出的 GBK）、**BOM**、**换行符**；混合换行符的文件保存后仍然混合，未改动的行尾逐字节不变。
- **原子写入**：写同目录临时文件 → `ReplaceFileW` / 重命名替换，保留原文件的属性与时间戳语义；替换失败时不得留下半截文件或临时残留。
- 无法编码的字符（例如 GBK 文件里输入了 emoji）：**保存前弹模态框**（`UX_SPEC.md` §3.5 唯一允许的模态场景之一），文案“有 N 个字符无法用 GBK 保存。”，三个选项“改用 UTF-8 保存”“仍然保存（替换为 ?）”“取消”。选“改用 UTF-8”时同时更新文档的编码与状态栏显示。
- 命令：`workbench.action.files.save`（`ctrl+s`）、`saveAs`（`ctrl+shift+s`）、`saveAll`、`saveFiles`、`workbench.files.action.saveAllInGroup`、`workbench.action.files.saveWithoutFormatting`（`ctrl+k ctrl+shift+s`，Rove 没有保存时格式化，等同于 `save`，但命令必须存在）。

### 2. 保存失败（`UX_SPEC.md` §6.4，均为第 4 级反馈：通知）

| 情况 | 处理 |
|---|---|
| 被其他程序占用（Unity 正在导入） | **自动重试一次**，仍失败才弹通知“无法保存 `Player.cs`：文件被其他程序占用。”按钮“重试”“另存为” |
| 文件有只读属性 | 通知，按钮“覆盖”（清除只读属性后保存）“另存为”；**不提供“以管理员身份保存”** |
| 磁盘上已被修改（保存冲突） | 通知，按钮“比较”“覆盖”“放弃本地修改”；**“比较”在对比视图（P2）完成前隐藏**，`files.saveConflictResolution` 为 `overwriteFileOnDisk` 时直接覆盖不提示 |

同一原因的通知不重复弹出，再次触发时更新已有通知中的次数（`UX_SPEC.md` §6.1 通用规则）。

### 3. 修改状态与关闭

- 脏标记：文档版本与“最后保存时的版本”比较；标签上的未保存圆点由 R17（编辑器组与标签） 绘制，本 issue 只提供状态与事件。
- 关闭有未保存修改的标签 / 窗口时弹模态框（`UX_SPEC.md` §6.1 第 5 级的典型场景）：“保存”“不保存”“取消”。`files.hotExit` 生效时这个模态框按 VS Code 被跳过——该分支由 R49（热退出与崩溃恢复）（M4）接管，本 issue 把开关点留好并默认走模态框。
- 还原：`workbench.action.files.revert`、`workbench.files.action.revertLocalChanges`、`workbench.files.action.acceptLocalChanges`（后两个是保存冲突通知的命令形式）。

### 4. 外部修改与自动重载（`FEATURES.md` §6，P0）

订阅 R15（工作区） 的文件事件：

- **本地没有修改**：静默重新加载，保持滚动位置与光标（走 R19（代码视图 Element） 的滚动定位接口），不弹任何提示；编码与换行符重新识别，若结果变化则更新状态栏。
- **本地有修改**：显示编辑器顶部提示条（第 3 级反馈），选项“重新加载（丢弃本地修改）”“保留本地修改”；不弹模态框——此时数据还没丢。
- **文件被删除**：标签标记为“已删除”，内容保留在缓冲里，下次保存视为新建写入。
- **自己保存触发的事件必须去重**：记录自己写入的路径、时间窗与内容哈希，匹配上的事件直接丢弃，否则每次保存都会自触发一次“外部修改”。
- 外部修改风暴（脚本连续改写）要合并：按路径去抖，最终状态一致即可，中间状态不必逐个重载，也不得堆积提示条。

### 5. `files.*` 设置

- **必须实现（P0）**：`files.encoding`（含语言级覆盖）、`files.eol`（只用于新建文件）、`files.readonlyFromPermissions` / `readonlyInclude` / `readonlyExclude`（判定在 R15（工作区），本 issue 消费判定结果决定能否写）。
- **一并实现的 P1 小项**（实现成本接近于零，不值得单开 issue）：`files.insertFinalNewline`、`files.trimFinalNewlines`、`files.trimTrailingWhitespace`、`files.saveConflictResolution`、`files.autoSave` / `autoSaveDelay` / `autoSaveWorkspaceFilesOnly` / `autoSaveWhenNoErrors`（没有问题提供方时视为“无问题”，R60（JSON/YAML/XML） 合并后自动生效）。保存时的文本变换一律走 R45（编辑核心模型） 的事务，和用户的改动合并成同一个撤销单元。
- 全部通过 R01（【接口先行 A1】架构与接口契约） 的设置读取接口获取，**绝不写回共用的设置文件**（`FEATURES.md` §13 规则 5）。

### 6. 状态栏的换行符统一动作

R27（状态栏条目）（M1）把“统一为 LF / CRLF”推迟到了 R45（编辑核心模型） / 本 issue 合并之后（见该 issue 第 26 行）。本 issue 登记 `workbench.action.editor.changeEOL`，并把“统一为 LF”“统一为 CRLF”补进换行符选择器：改写走 R45（编辑核心模型） 的事务（可一次撤销），落盘走本 issue 的写入路径。编码选择器中的“通过编码保存”同样在此补齐（见 R27（状态栏条目） 第 25 行）。

### 6.1 未命名文档

`workbench.action.files.newUntitledFile`（`ctrl+n`，P0）与 `workbench.action.files.newFile`：新建只在内存中的未命名文档（`Untitled-1` 等），带修改标记；关闭时按“未保存修改”提示；首次保存走“另存为”。编码使用 `files.encoding`，换行符使用 `files.eol`。热退出时如何保留未命名文档由 R49（热退出与崩溃恢复） 负责。

### 7. 登记与替换

新增命令、设置项、界面字符串通过 R01（【接口先行 A1】架构与接口契约） 的登记机制加入，不得写死；所有用户可见文案按 `UX_SPEC.md` §6 的风格（先说发生了什么，再说可以怎么做，不带“错误：”前缀）。R02（【接口先行 A2】行走骨架） 中没有本 issue 对应的 `SKELETON(...)` 标记，只在 `docs/ARCHITECTURE.md` 中新增 / 更新自己的一行。不得在本 PR 中修改 R01（【接口先行 A1】架构与接口契约） 的接口。

### 补充：去除行尾空格时跳过字符串与正则

`files.trimTrailingWhitespaceInRegexAndStrings`（默认 true）：去除行尾空格时，跳过字符串与正则字面量内部的行尾，区间判断使用 R09（tree-sitter 集成） 的 token。

## 验收标准

- [ ] `ctrl+n` 新建未命名文档，可以编辑；关闭时提示保存；保存时打开“另存为”，按 `files.encoding` / `files.eol` 写入
- [ ] **编码往返**：GBK + CRLF、UTF-8 带 BOM、UTF-16 LE/BE、混合换行符五类文件，各编辑一处后保存，**除改动处外字节完全一致**
- [ ] 混合换行符文件保存后仍为混合，状态栏仍显示 `混合`；“统一为 LF / CRLF”执行后全文一致且可一次撤销
- [ ] 无法编码字符：GBK 文件中输入 emoji 后保存弹模态框，三个按钮行为各有用例（“改用 UTF-8”后文件变为 UTF-8 且状态栏同步）
- [ ] 原子写入：写入过程中强杀进程后，原文件保持完整（至少用注入故障点的测试验证一次），目录下无临时残留
- [ ] 占用重试：用一个持有独占句柄的辅助进程模拟，断言**先自动重试一次**再弹通知，按钮“重试”“另存为”可用
- [ ] 只读属性文件：通知含“覆盖”“另存为”，选“覆盖”后属性被清除并保存成功；**界面上不存在任何管理员提权入口**
- [ ] 保存冲突：外部修改后再保存，通知出现且“比较”按钮隐藏；“覆盖”“放弃本地修改”各有用例；`files.saveConflictResolution = overwriteFileOnDisk` 时不提示
- [ ] 外部修改：无本地修改时静默重载且滚动位置与光标不变；有本地修改时出现提示条且两个选项正确；文件被删除时标签标记“已删除”
- [ ] **外部脚本连续修改同一文件 100 次**：最终内容与磁盘一致，提示不堆积、不重复弹通知（场景与 R50（【集成验收】M3） 共用）
- [ ] 自己保存**不会**触发“外部修改”提示（连续保存 20 次断言零误报）
- [ ] `files.insertFinalNewline` / `trimFinalNewlines` / `trimTrailingWhitespace` / `autoSave` 各有参数化用例；保存时的变换与用户改动合并为一个撤销单元
- [ ] 关闭未保存文件弹模态框，“保存 / 不保存 / 取消”三条路径各有用例
- [ ] 新增的命令、设置项、界面字符串都经由登记机制，无硬编码；`cargo tree -p rove-buffer -i gpui` 为空
- [ ] R02（【接口先行 A2】行走骨架） 的端到端测试仍然通过；新增“编辑 → 保存 → 外部修改 → 重载”的集成测试

## 风险与提示

- **去重是这个 issue 最容易留坑的地方**。只按路径 + 时间窗去重，在慢盘上会漏判；只按内容哈希去重，在“保存后外部立刻改回同样内容”时会误判。建议两者结合，并在测试里把保存与外部写入的时序刻意交错。
- 原子替换在 Windows 上有细节：目标文件被其他进程以 `FILE_SHARE_DELETE` 之外的方式打开时替换会失败，这正是“被 Unity 占用”的典型表现；不要把它当成未知错误，要落到 §6.4 的“占用”分支。
- 模态框只能用于第 5 级场景。保存失败、保存冲突、外部修改都**不是**模态框——`UX_SPEC.md` §6.1 把通知和提示条分得很清楚，写成模态框会让“脚本在后台改文件”变成不断阻塞的弹窗。
- 不要在保存路径上顺手做格式化或缩进统一。`saveWithoutFormatting` 之所以等同于 `save`，正是因为 Rove 没有保存时格式化（`FEATURES.md` §4：C# 不做格式化）。
- 文件末尾换行与 `trimFinalNewlines` 的组合容易互相打架（两者默认都是 false）。按 VS Code 的顺序执行：先去行尾空格、再去末尾多余空行、最后补末尾换行。
