## 背景

C# 精确导航需要一个 .NET 索引进程，而 Rove 主程序是纯 Rust、发布包预算 < 30 MB（`PROJECT_CHARTER` §6）。`LANGUAGE_INTELLIGENCE` §3.3 的"分发"一节定了做法：索引进程以 **self-contained 方式发布，内置 .NET 运行时，用户无需安装 SDK**，体积估计 60–90 MB，因此**作为与主程序分开的可选组件**（已确认接受，2026-11-09）。主程序没有这个组件也能运行，只是 C# 导航停留在 L0/L1。

本 issue 把这件事落地：发布配置、体积、安装位置、版本握手，以及"组件缺失"时的降级与界面提示。它是 M2 的最后一环，也是 R75（Windows 发布流水线、安装包、体积守护、第三方许可声明） 的前置。

## 目标

### 1. self-contained 发布

`dotnet publish -r win-x64 --self-contained`，配置写进 `tools/rove-indexer-cs/RoveIndexer.csproj`（或单独的发布 profile）。

- **开启 trim 并逐项验证 Roslyn 的反射需求**：Roslyn 大量使用反射（分析器加载、`SymbolDisplayFormat`、序列化），trim 很可能把需要的类型剪掉。要在两个真实测试项目上实跑验证，而不是只看能不能启动。
- trim 不可行时记录原因并退回不 trim，这是可接受的结果——但要有结论，不能含糊。
- 考虑 ReadyToRun（影响启动时间与体积，两者都测一下再决定）。
- **报告体积**，对照 60–90 MB 的预算；超出时说明构成（运行时 / Roslyn / 自己的代码各占多少）。

### 2. 协议与版本握手

Rove 启动索引进程时交换协议版本（握手消息由 R35（增量索引） 的常驻协议预留，本 issue 定稿版本协商规则）：

- 版本兼容 → 正常工作；
- **版本不兼容 → 提示用户更新组件，并降级到 L1/L0**，不要试图用不兼容的协议硬跑；
- 索引文件的格式版本与索引进程版本已经写在索引头部（R32（C# 索引格式 v2）），R36（索引生命周期与状态） 的有效性检查会据此重建。本 issue 要保证**组件版本、协议版本、索引格式版本三者的对应关系有一张明确的表**，写进 `docs/CS_INDEX_FORMAT.md` 或 `LANGUAGE_INTELLIGENCE.md` §3.3。

### 3. 安装位置与发现规则

默认安装在 `%LOCALAPPDATA%\Rove\components\indexer-cs\`，发现规则（查找顺序、版本目录布局、同时存在多个版本时选哪个）与 R75（Windows 发布流水线、安装包、体积守护、第三方许可声明） 的安装包约定一致，**两边在开工前对齐**。R36（索引生命周期与状态） 中那段"开发路径"的查找逻辑在本 issue 替换为正式规则。

组件是可选的：主安装包不含它，安装器中是一个可勾选项或事后下载安装的独立包（具体形式与 R75（Windows 发布流水线、安装包、体积守护、第三方许可声明） 协商；**Rove 运行期不得主动联网下载**，组件的获取由用户发起）。

### 4. 组件缺失时的降级与提示

没有安装组件时，C# 导航降级到 L0/L1（由 R38（查询路由与未保存修改的位置映射） 处理），界面上按 `UX_SPEC` §2.1 的"未安装语义组件"一行显示：

- 状态栏：`$(info) C# 基础导航`；
- 悬停：跳转和引用是近似结果，安装语义组件后可以获得精确结果；
- 点击：打开说明页面，**内容包括安装方法**。

状态栏条目本身由 R36（索引生命周期与状态） 实现，本 issue 负责提供"组件是否存在、版本是否兼容"的判定，以及说明页面的内容与提示文案"安装语义组件以获得精确导航"（通过界面字符串表登记，不要写死）。

### 5. 在干净的 Windows 上验证

在一台**没有安装 .NET 的干净 Windows**（虚拟机或 Windows Sandbox）上实跑：组件能启动、能完成一次全量索引、能进入常驻模式。这是 self-contained 的唯一有效验证方式——开发机上装着 SDK，什么都看不出来。

## 不包含

- 主程序的发布流水线、安装包、体积守护、第三方许可声明（R75（Windows 发布流水线、安装包、体积守护、第三方许可声明）；本 issue 只提供组件包和它的安装位置约定）。
- 常驻协议的消息内容与增量逻辑（R35（增量索引））。
- 索引进程的性能（R33（索引进程性能优化））、索引格式（R32（C# 索引格式 v2））。
- 状态栏条目与说明页面的界面实现（R36（索引生命周期与状态）、R16（工作台））。
- 自动更新组件：首版不做，在 PR 中记录这个决定。

## 验收标准

- [ ] **在一台没有安装 .NET 的干净 Windows 上（虚拟机或 Windows Sandbox），组件可以运行**：完成一次中型项目的全量索引，并能进入常驻模式接收一次文件变更
- [ ] **体积报告**：发布包解压后的体积、安装包体积、trim 前后对比，对照 60–90 MB 预算
- [ ] trim 有明确结论：开启（并说明验证过哪些反射路径）或不开启（并说明原因）
- [ ] 开启 trim 的版本在两个测试项目（`ROVE_TEST_UNITY_MEDIUM` / `ROVE_TEST_UNITY_LARGE`）上实跑通过，未解析名称占比与不 trim 的版本一致
- [ ] 版本握手：协议版本不匹配时，Rove 给出明确提示并降级到 L1/L0，不崩溃、不卡住，有测试
- [ ] 组件版本 / 协议版本 / 索引格式版本的对应关系表已写入文档
- [ ] 组件缺失时：状态栏显示"未安装语义组件"状态，点击打开含安装方法的说明页面，C# 导航降级到 L0/L1，有集成测试
- [ ] 安装位置与发现规则与 R75（Windows 发布流水线、安装包、体积守护、第三方许可声明） 对齐，PR 中给出对齐结论；R36（索引生命周期与状态） 中的开发路径查找已替换为正式规则
- [ ] 所有新增用户可见文案都通过界面字符串表登记，没有写死
- [ ] 组件在运行期不发起任何网络请求（在干净环境上用抓包或防火墙验证）
- [ ] R02（【接口先行 A2】行走骨架） 的端到端测试继续通过

## 风险与提示

- **trim 是这个 issue 最大的不确定性**。Roslyn 的反射面很广，trim 后的失败往往不是启动崩溃，而是"某类符号突然解析不出来"。所以验收标准里要求比对未解析名称占比——只验证"能跑起来"是不够的。如果 trim 省下来的体积有限而风险很高，不 trim 是完全可以接受的结论。
- 60–90 MB 是估算，不是预算上限。真超了也不是灾难（组件是可选的、单独下载的），但要在 PR 里讲清楚体积都花在哪儿，并说明有没有便宜的优化（例如裁掉用不到的 Roslyn 语言支持）。
- 版本握手要能"向前看"：用户装了新组件、Rove 还是旧的，这种组合也会发生。握手规则要同时覆盖"组件太新"和"组件太旧"两个方向。
- Windows Sandbox 每次启动都是全新环境，很适合做这个验证，但它默认没有网络限制也没有持久化。验证步骤（怎么把包拷进去、跑什么命令、看什么输出）要写进 PR，下次发版时还要再跑一遍。
- 这是 M2 里唯一碰发布配置的 issue，和 R75（Windows 发布流水线、安装包、体积守护、第三方许可声明） 的接缝（安装位置、可选组件的呈现方式）最容易对不上。**开工第一件事是和 R75（Windows 发布流水线、安装包、体积守护、第三方许可声明） 对齐这两点**，不要做完才发现路径约定不一致。
