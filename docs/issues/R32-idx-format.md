> 认领前请阅读 `AGENTS.md`、`docs/ARCHITECTURE.md`（R01 完成后）与 `docs/issues/README.md`。前置依赖全部合并后才能开工。

## 背景

M0 已经证明"预计算语义索引"这条路走得通（`M0_LANG_SPIKE_REPORT` 的结论），但 v1 格式本身有几个硬伤，`CS_INDEX_FORMAT.md` 的"已知待改进"一节已经列出：

- 大型项目的索引 **303 MB**，超出 `LANGUAGE_INTELLIGENCE` §6 的 200 MB 目标；
- 局部变量 / 参数 / lambda 的符号键里写着完整路径（`@文件路径:声明偏移:名称`），把字符串段撑大；
- 列号是 UTF-16 坐标（Roslyn 坐标），而 Rove 内部用 UTF-8 字节，每次查询都要在读取侧换算；
- 打开索引时要遍历整个字符串段来建立"路径 → 文件"的 HashMap。热缓存只要几毫秒，但 M0 实测索引放在机械硬盘上且不在系统缓存中时，**打开要 3.4 s**，前 200 次跳转 p99 166 ms、最慢 2.8 s；
- 外部符号没有签名和文档，元数据视图无从谈起；
- 头部只有一个格式版本号，判断不了"这份索引是哪个版本的索引进程、用什么项目配置生成的"。

本 issue 做格式 v2，一次性把这些坑填上。**写入方 `tools/rove-indexer-cs/IndexWriter.cs`、读取方 `crates/rove-lang-cs/src/index.rs`、文档 `docs/CS_INDEX_FORMAT.md`、基准 `crates/rove-lang-cs/examples/cs_index_bench.rs` 必须在同一个 PR 里一起改**，否则谁都跑不起来。

索引文件格式是 .NET 索引进程与 Rust 读取侧之间的**契约**：索引进程不在 R01（【接口先行 A1】架构与接口契约） 的 Rust 接口体系内，但这份格式文档对 R33（索引进程性能优化）、R34（外部符号元数据视图的生成）、R35（增量索引）、R36（索引生命周期与状态） 具有同等约束力，改它要像改契约一样慎重。

## 目标

### 1. 二进制局部键

局部变量、参数、类型参数、局部函数、lambda 的键改为 **(文件序号 u32, 声明处字节偏移 u32)** 的二进制键，不再进字符串段。类型与成员仍用 `程序集名|文档注释 ID`（跨项目引用同一个源码符号时键相同，这个性质必须保留）。

### 2. 紧凑的出现位置编码

v1 每条出现位置占 20 字节。改为分块定长或按行差分的变长编码都可以，但必须满足：

- "文件 + (行, 列) → 出现位置"和"符号 → 出现位置列表"两类查询仍然是 **O(log n)**（分块时块内可以线性扫，块数要能二分）；
- 不能为了压缩体积把随机查询变成顺序扫描——M0 实测跳转 avg 2–4 µs，这个量级不能退。

### 3. UTF-8 字节列

列号改为**UTF-8 字节列，转换在索引进程中完成**（Roslyn 给的是 UTF-16 列，索引进程手里有源文件文本，换算最便宜）。读取侧从此不再做 UTF-16 转换。列号在 Rust 侧用 R01（【接口先行 A1】架构与接口契约） 在 `rove-base` 中定义的"UTF-8 列"新类型表达，不要用裸 `u32`。本 issue 的前置依赖里没有 R01（【接口先行 A1】架构与接口契约），如果开工时它还没合并，先在 `rove-lang-cs` 内部放一个等价的新类型，合并后替换，**不要在本 PR 里修改契约**。

同时在 PR 中说明：R07（文本缓冲） 为 v1 实现的 UTF-8 ↔ UTF-16 列转换在 C# 导航链路上不再需要（但它本身是 `rove-buffer` 的能力，不要删）。

### 4. 排序的路径表

文件表按相对路径排序后存放（v1 已经按 `StringComparer.Ordinal` 排了，但读取侧没利用），查找时在路径表上二分。**打开索引时不读取字符串段、不建 HashMap**，这是把冷缓存打开耗时从 3.4 s 拉回来的关键一步。

### 5. 为 R34（外部符号元数据视图的生成） 预留段

v1 的第 8 段是"保留：文档注释"。v2 明确划出三个段：外部符号的签名、XML 文档注释、以及"元数据视图"的文本与其中每个成员的位置。本 issue 只定义段的布局、写空段、读取侧能正确读到空段；内容由 R34（外部符号元数据视图的生成） 填。

### 5.1 不生效的预处理区域

按文件记录 `#if` / `#elif` / `#else` 中按项目宏判定为不生效的行区间（Roslyn 解析时已经得到这项数据，见 `LANGUAGE_INTELLIGENCE.md` §3.3），供 R58（C# 语义高亮与不生效预处理代码置灰） 置灰显示（D9）。

### 6. 头部

加入：格式版本、**生成这份索引的索引进程版本**、**项目配置哈希**（csproj / asmdef 集合、宏、引用列表的哈希）。R36（索引生命周期与状态） 用这三项判断缓存是否失效。再预留若干字段给 R35（增量索引） 的覆盖层（段数可扩展，老读取方遇到更高的格式版本要明确报错而不是乱读）。

### 7. 健壮性

索引文件可能被写了一半就断电、被杀毒软件截断、被用户手工删掉一截。读取侧对**损坏或截断的文件一律返回错误，绝不 panic**：段表越界、偏移重叠、字符串偏移不单调、计数溢出都要在 `open()` 里查出来。

## 不包含

- 索引进程的耗时与内存优化（R33（索引进程性能优化））。
- 元数据视图的内容生成（R34（外部符号元数据视图的生成））。
- 覆盖层的生成与合并逻辑（R35（增量索引），本 issue 只预留头部字段）。
- 缓存目录、有效性检查、预读（R36（索引生命周期与状态），本 issue 只提供它判断所需的头部字段）。
- 导航查询接口的形状（R01（【接口先行 A1】架构与接口契约） 与 R38（查询路由与未保存修改的位置映射））。

## 验收标准

- [ ] 大型测试项目（`ROVE_TEST_UNITY_LARGE`）的索引 **< 170 MB**（总目标 200 MB，为 R34（外部符号元数据视图的生成） 的元数据段预留 30 MB）；中型项目（`ROVE_TEST_UNITY_MEDIUM`）同步给出数字，与 v1 的 303 MB / 94 MB 对比
- [ ] 打开索引（热缓存）< 5 ms，且用计数或日志证明**打开过程没有触达字符串段**
- [ ] `cs_index_bench` 在两个项目上各 20,000 次随机查询：定义跳转与查找引用的 avg / p99 / max 不差于 v1（附对比表）
- [ ] 路径 → 文件序号改为二分查找，有一个"路径不存在"和"路径为前缀"的边界用例
- [ ] 列号为 UTF-8 字节列：含中文注释、emoji、代理对的源文件中，索引给出的列与 Rust 侧按字节切片得到的标识符文本一致
- [ ] 局部符号不再在字符串段中出现完整路径（用一个扫描字符串段的测试断言）
- [ ] 随机截断测试：对一份真实索引在随机位置截断 1000 次，`CsIndex::open` 全部返回 `Err`，无 panic；另有一个对头部与段表做随机字节翻转的 fuzz 或属性测试
- [ ] `docs/CS_INDEX_FORMAT.md` 更新为 v2（段表、编码方式、符号键、头部字段都要写全），"已知待改进"中被解决的条目删掉
- [ ] `IndexWriter.cs`、`index.rs`、`cs_index_bench.rs` 在同一 PR 中更新，并在两个测试项目上实跑通过

## 风险与提示

- **索引进程的文件按 R32（C# 索引格式 v2） → R33（索引进程性能优化） → R34（外部符号元数据视图的生成） / R35（增量索引） 的顺序串行修改**。本 issue 是第一棒，合并后其他几个才动手；开工期间不要有人并行改 `tools/rove-indexer-cs/`。
- 压缩和查询速度是一对矛盾。先用真实数据量算一遍：4.85 M 个出现位置，每省 4 字节就是 19 MB。优先砍掉字符串段（局部键）和 padding，再考虑变长编码；不要一上来就上复杂的压缩方案。
- 格式变了，R39（C# 导航准确率测试集） 的运行器也要跟着适配。那个 issue 要求把格式相关的部分收在一个适配层里，本 PR 合并后只需改那一处——合并前先确认它确实做到了。
- 头部里的"项目配置哈希"要定清楚**哈希的输入是什么**（哪些文件、哪些字段、是否含顺序）。定得太宽，Unity 一刷新就全量重建；定得太窄，配置变了却不重建，结果是错的。这个定义写进 `CS_INDEX_FORMAT.md`，R36（索引生命周期与状态） 直接照用。
