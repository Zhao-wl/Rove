# R08 文件大小分级与超大文件：内存映射、分块行索引、追加内容的增量索引

| 里程碑 | 难度 | 领域 | 并行批次 | 前置依赖 | 被依赖 |
|---|---|---|---|---|---|
| M1 只读阅读器 | 3 困难 | core | 第 4 批 | R07（文本缓冲） | R22（超大文件与超长行的界面）、R27（状态栏条目）、R31（【集成验收】M1） |

> 认领前请阅读 `AGENTS.md`、`docs/ARCHITECTURE.md`（R01 完成后）与 `docs/issues/README.md`。前置依赖全部合并后才能开工。

## 背景

`UX_SPEC` §3.1 要求"任何大小的文本文件都能秒开"，并把文件分成三级处理。M0 验证了"mmap + 首屏同步索引 1 MiB + 后台分块索引"这个策略完全成立：`Doc::open` 恒定在 1 ms 量级、与文件大小无关，1 GB 文件打开到首屏 444 ms 中文件本身只贡献 1 ms（`M0_UI_SPIKE_REPORT` §4.3）。同时也量化出一个必须解决的问题：**1429 万行的 `Vec<u64>` 行索引本身就要 114 MB**（§4.2），对 GB 级文件太重。

实现放在 R01（【接口先行 A1】架构与接口契约） 定义的 `TextSource` 背后，与 R07（文本缓冲） 的普通文档实现同一个 trait，代码视图只面向 trait。本 PR 不修改契约接口。

## 目标

### 1. 文件大小分级（`UX_SPEC` §3.1）

| 级别 | 判定条件 | 可编辑 |
|---|---|---|
| 普通 | 其余情况 | 是 |
| 大文件 | ≥ 20 MB 或 ≥ 30 万行（与 VS Code `editor.largeFileOptimizations` 的阈值一致；该设置为 `false` 时**不启用这一级**） | 是 |
| 超大文件 | ≥ `rove.largeFile.threshold`（默认 `67108864`，即 64 MB） | **否，只读** |

分级结果和"被关闭的功能清单"（大文件：缩略图、粘性滚动、括号对着色、同名高亮、语义高亮、基于语法的折叠；超大文件：再加语法高亮、所有折叠、软换行、替换）通过文档模型向上层暴露，供状态栏悬停时逐项列出。界面表现由 R22（超大文件与超长行的界面） 实现，本 issue 只提供数据。

### 2. 超大文件：内存映射

`memmap2` 映射文件，打开时不把整个文件读进内存；只读原因标记为"超大文件"（`UX_SPEC` §3.4 的只读来源 1），**不允许通过"在此会话中切换只读"解除**。

### 3. 分块行索引

每 256 行存一个 `u64` 锚点，块内各行用 `u32` 相对偏移（对 < 4 GB 的文件足够）。目标是把 1429 万行的索引内存压到 M0 方案的一半以下。

构建策略沿用 M0 原型：打开时**同步**索引头部 1 MiB（保证首屏立即可用），其余在后台线程按 32 MiB 分块用 `memchr` 扫描，对外提供"已知行数 + 进度百分比"。索引未完成期间可滚动的范围持续增长，滚动条按字节位置估算（`UX_SPEC` §3.2）。

### 4. 追加内容的增量更新

文件只在末尾增长时（日志，典型是 Unity 的 `Editor.log`）**只索引新增部分**并保持滚动位置，不重建整个索引；R66（跟随文件末尾、格式化后查看） 的"跟随文件末尾"依赖这一点。文件被截断、或中间内容被改写时，重新建立映射：不能崩溃，也不能给出错误的行号（宁可整体重建）。通过文件大小 + 修改时间 + 头部校验判断是"追加"还是"改写"。

### 5. 超长行

单行超过 `editor.stopRenderingLineAfter`（默认 10000 个字符）时由界面截断显示（`UX_SPEC` §3.3）。缓冲层要提供"按字节区间取子串"和"整行字节长度"，让界面能只整形可见的一段，**不要一次性整形整行**。M0 两个原型都用 `MAX_LINE_BYTES = 2048` 直接截断来回避病态行（§8 第 10 项），这个做法不能照抄到产品里。

## 不包含

- 超大文件的界面（只读提示条、行索引进度、转到行等待、流式查找、截断标记）：R22（超大文件与超长行的界面）。
- 跟随文件末尾与"格式化后查看"：R66（跟随文件末尾、格式化后查看）。
- 编码识别、BOM、换行符（R07（文本缓冲）；超大文件按 `files.encoding` 或 BOM 处理，不做代价高的全文猜测，这一取舍要在 PR 中写明）。

## 验收标准

- [ ] 1 GB 测试文件（R04（性能基准与预算守护） 的 `big1g.txt`）首屏可用 < 100 ms，热缓存下全量索引 < 1 s（M0 基线 0.58–0.60 s）
- [ ] 1429 万行的索引内存 < 60 MB（M0 的 `Vec<u64>` 基线为 114 MB），在 PR 中给出实测值
- [ ] 转到任意第 N 行 < 1 ms（索引已完成时）
- [ ] 三级分级的判定有真值表测试，含 `editor.largeFileOptimizations = false` 时大文件级不生效
- [ ] 追加 1 MB 后只增量索引，耗时与追加量成正比而与文件总大小无关；滚动位置保持
- [ ] 文件在外部被截断 / 中间改写时不崩溃，且后续行号正确
- [ ] 边界用例：末尾没有换行符、全是空行、纯 CRLF、单行 100 MB、空文件
- [ ] 超长行的"按区间取子串"有基准，取任意一段的耗时与行长无关
- [ ] 新增集成测试覆盖"打开超大文件 → 只读原因 → 进度 → 转到行"；R02（【接口先行 A2】行走骨架） 的端到端测试继续通过
- [ ] `cargo tree -p rove-buffer -i gpui` 为空

## 风险与提示

- 1 GB 文件的工作集约 1.2 GB 是 **mmap 的文件页被后台索引线程全部触达**造成的。这些页是文件支持、可回收的，不等于真实占用；报告与基准里要区分工作集和私有提交（M0 §4.2），不要误判为内存泄漏。
- 后台索引线程会把整个文件读一遍。在机械硬盘上这是 ~3.1 s 的顺序读（M0 实测 330 MB/s），期间要让出 I/O，不能影响首屏交互。
- "已知行数"是个会变的量。接口上要让调用方明确区分"当前已知行数"和"最终行数未知"，否则滚动条和"转到行"会在索引完成前后给出不一致的行为。
