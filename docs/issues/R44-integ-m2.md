## 背景

M2 的十三个 issue 分布在三个层次：C# 索引进程（格式、性能、增量、元数据）、查询层（生命周期、L1、路由）、界面（导航交互、速览、元数据视图）。每一层都有自己的测试，但**接缝只有连起来走一遍才会暴露**：保存文件后高亮是不是立刻从精确退化成近似、再静默变回精确；索引原子替换时打开着的元数据视图会不会显示旧内容；没装语义组件的干净机器上 `Shift+F12` 是不是还能用；机械硬盘上冷启动的前几秒跳转会不会卡住。

本 issue 由**一个会话独占**，开始前 M2 的全部前置 issue 都已合并。产出是一份可核对的验收报告和对接缝缺陷的修复。

`PLAN.md` 的 M2 完成标准是一句很硬的话：**跳转和引用体验超过 VS Code**（验收口径：导航准确率测试集通过、响应时间指标达标）。本 issue 负责证明或证伪它。此外 `M0_LANG_SPIKE_REPORT.md` 里有三项**明确挂在 M2 名下**的待办要在这里结清：SSD / NVMe 的冷缓存数据补测（§2 的 ⚠ 注）、人工测试集的逐例验证（§“下一步”第 4 项）、Source Generators 是否真的被加载的复核（§“验证中发现的真实问题”第 4 条）。

必读：`PLAN.md`（M2 一行）、`PROJECT_CHARTER.md` §6、`UX_SPEC.md` §2 与 §4.1、`FEATURES.md` §5 与 §12（D3）、`LANGUAGE_INTELLIGENCE.md` 全文、`M0_LANG_SPIKE_REPORT.md` 全文、`docs/compat/KEYBINDINGS.md`（导航）、`SETTINGS.md`。

## 目标

### 1. 导航准确率测试集：精确层必须 100%

- 用 R39（C# 导航准确率测试集） 的运行器（`cargo xtask nav-check`）在两个 Unity 项目上跑完 200 个用例，**语义索引就绪（精确层）时要求全部通过**；锚点失效的用例先修锚点，不能用“过期”掩盖失败。
- 报告按 R39（C# 导航准确率测试集） 的场景分类逐类给出准确率：`var` 推断、链式调用、重载、扩展方法、泛型（含 `GetComponent<T>`）、继承与重写、接口实现、partial、Lambda/LINQ、`#if UNITY_EDITOR`、Unity API（外部符号）、局部变量与参数、事件 / 委托、运算符重载、索引器、类型引用。
- 近似层（L0/L1）**不要求 100%**，但要给出每一类的实际数字，作为“索引构建期间体验如何”的基线。
- 不通过的用例逐条给出结论：是索引缺陷、路由缺陷、还是用例本身写错。

### 2. 界面手工抽查（≥ 20 例）

从测试集中抽 ≥ 20 个用例在界面上手工走一遍（覆盖上面至少 8 个分类），每例记录：`F12` 是否落到正确的行、悬停签名是否正确、`Shift+F12` 的结果数是否与查询层一致、精确 / 近似标记是否符合 `UX_SPEC.md` §2.2。这一条是 R40（C# 导航交互） 验收标准的放大版，重点看的是**界面与查询层的结果是否一致**。

### 4. 性能预算核对

用 R04（性能基准与预算守护） 的工具链在参考设备（8 核 / 16 GB / SSD / 集显）上实测并与 `perf/budgets.toml` 比对，每项给出中位数与 p99，**热缓存与冷缓存分开报**：

| 指标 | 预算 | 口径 |
|---|---|---|
| 定义跳转（查询侧） | < 16 ms | `PROJECT_CHARTER.md` §6；M0 实测 3.5 µs / p99 12.9 µs |
| 查找引用（查询侧） | < 50 ms | 同上；最重符号 M0 实测 1.95 ms |
| `F12` → 目标行画面完成 | < 50 ms | R40（C# 导航交互） 的端到端口径（目标文件已打开） |
| 速览首次绘制（最重符号） | < 100 ms | R41（速览窗口） |
| 单文件增量更新 | < 300 ms | R35（增量索引） |
| 首次全量索引（大型） | < 90 s，峰值 < 3 GB，索引 < 200 MB | R33（索引进程性能优化）、R32（C# 索引格式 v2） |
| 冷缓存下的首批跳转 | 记录实测值 | M0 在 HDD 上为 p50 9.0 ms / p99 166 ms / max 2.8 s，本次要给出预读生效后的数字 |

M1 已核对过的界面预算（每帧 CPU、快速打开按键延迟等）在加入导航装饰后**重测一遍**，确认没有回退。

## 风险与提示

- 本里程碑的接缝集中在**精确度标记的传递链**：R38（查询路由与未保存修改的位置映射） 打标记 → R40（C# 导航交互） 决定提示 → R41（速览窗口） 写进标题 → R42（元数据视图界面） 决定是否打开视图。任何一环把标记丢了，界面都会“看起来正常”但其实在骗人。建议专门设计一组用例，强制索引处于构建中 / 已就绪 / 文件已修改三种状态，逐链路断言。
- 第二个高风险点是**索引原子替换的那一瞬间**：替换时可能有速览窗口开着、元数据视图开着、同名高亮正显示着。这些视图持有的位置在新索引中可能已经失效，必须验证它们会刷新而不是显示旧数据或崩溃。
- 测试项目在验证期间会被 Unity 和其他工具频繁改动（`M0_LANG_SPIKE_REPORT.md` 第 1 条：中型项目 1 小时内改动了 790 个文件）。计时类场景要先确认 Unity 没有在后台导入，否则数字不可比；报告中注明每次测量时的项目状态。
- “体验超过 VS Code”这句结论很容易写成主观判断。用数据说话，并且**允许得出否定结论**——一份诚实的未达标清单比一份好看的报告有用得多（参考 `M0_UI_SPIKE_REPORT.md` §8 的写法）。
- 场景 7、8 需要能手工破坏环境（结束进程、移走组件、放旧版本组件）。先确认这些操作不会污染 `%LOCALAPPDATA%\Rove` 下的真实缓存，建议用 `rove.index.cacheDir` 指向临时目录来做。
- 不要把“顺手改好一点”带进这个 PR。本 issue 的价值是如实记录与修接缝，不是补功能。
