## 背景

M1 的十几个 issue 由多个会话并行完成，各自的测试都只覆盖自己那一块。**接缝问题只有把完整流程走一遍才会暴露**：搜索结果打开的 `.md` 是不是源码、GBK 文件重新打开编码后状态栏有没有同步、从 VS Code 改了主题 Rove 有没有实时生效、150% 缩放下命令面板会不会错位。

本 issue 由**一个会话独占**，在它开始前 M1 的全部前置 issue 都已合并。它的产出是一份可核对的验收报告，以及对接缝缺陷的修复。

`PLAN.md` 的 M1 完成标准是一句很硬的话：**在两个 Unity 测试项目中，日常“看代码”不需要再打开 VS Code；性能指标达标**。本 issue 负责证明或证伪这句话。

必读：`PLAN.md`（M1 一行）、`PROJECT_CHARTER.md` §6（性能指标）与 §7（Windows 专项风险）、`FEATURES.md`、`UX_SPEC.md` 全文、`docs/compat/*`。

### 2. 扩展端到端测试套件

在 R02（【接口先行 A2】行走骨架） 的端到端测试基础上，把上述场景中**可自动化的部分**加进 `cargo test --workspace`（至少覆盖：GBK 文件、混合换行符文件、`.md` 默认预览、只读文件、搜索结果打开源码、快速打开、大纲与面包屑、共用设置热加载）。不可自动化的部分（截图、跨显示器拖动、从 VS Code 实时改设置）以清单 + 截图的形式记录在报告中。

### 3. 性能预算核对

用 R04（性能基准与预算守护） 的工具链在参考设备上实测并与 `perf/budgets.toml` 比对：冷启动到可交互 < 400 ms、空窗口常驻内存 < 60 MB、打开 1 GB 文件 < 1 s 且滚动稳定、连续滚动每帧 CPU < 1 ms、快速打开每次按键 < 16 ms、搜索首批 < 100 ms / 全量 < 2 s、面包屑更新 < 1 ms。每项给出中位数与 p99，超预算的写明差距与原因。

### 4. `SKELETON` 标记审计

检查代码中不再存在任何 M1 键名的 `SKELETON(...)` 标记（`workspace`、`explorer`、`groups`、`buffer`、`syntax`、`theme`、`codeview`、`statusbar`、`quickopen`、`keys` 等），并且 `docs/ARCHITECTURE.md` 的“最简实现 → 负责替换的 issue”对照表与代码一致。还有残留的，要么在本 issue 中补掉，要么开 issue 并在报告中列明。

### 5. 修复接缝缺陷

- 只修**接缝性质**的小缺陷（状态没同步、来源语义丢失、空状态文案不对、登记遗漏等）。
- 牵涉某个 issue 核心实现的较大问题，**开新 issue** 并在报告中记录，不在本 PR 里重写别人的模块。
- 发现接口缺陷时按契约变更流程单独提小 PR，**不在本 PR 中修改 R01（【接口先行 A1】架构与接口契约） 的接口**。
- 修复中新增的任何命令、设置项、颜色键、界面字符串，一律通过 R01（【接口先行 A1】架构与接口契约） 的登记机制加入。

### 6. 产出 `docs/M1_ACCEPTANCE_REPORT.md`

内容：环境信息（机器配置、显示缩放、两个 Unity 项目的版本与规模）、场景清单逐条结果、性能实测表与预算对照、`SKELETON` 审计结果、本 issue 修复的缺陷清单、开出的后续 issue 清单、以及对 `PLAN.md` M1 完成标准的明确结论（达成 / 未达成及缺口）。

## 风险与提示

- 最容易出问题的是**跨 issue 的“来源语义”**：同一个 `.md`，从文件树打开是预览、从搜索结果打开是源码；同一个文件，从快速打开进入是预览标签、双击是固定标签。这类语义没有单元测试能覆盖，必须手工走一遍。
- 两个 Unity 项目的差异要用足：中型项目验证交互正确性，大型项目（约 2.1 万个 `.cs`）验证性能与排除规则。
- 不要把“顺手改好一点”带进这个 PR。本 issue 的价值是**如实记录**，一份诚实的未达标清单比一份好看的报告有用得多（参考 `M0_UI_SPIKE_REPORT.md` §8 的写法）。
- 场景 13 需要本机装有 VS Code。没有时按 FEATURES §13 规则 1，在同样的位置手工创建共用文件来模拟，并在报告中注明。
