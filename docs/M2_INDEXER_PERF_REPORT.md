# M2 索引进程性能报告（#33）

> 日期：2026-11-12 · 环境：i7-11700（8 核 16 线程）/ 48 GB / Windows 11 · .NET 9 + Roslyn 5.9.0
> 代码：`tools/rove-indexer-cs`（索引进程 1.0.3）。M0 的数据见 [M0_LANG_SPIKE_REPORT](M0_LANG_SPIKE_REPORT.md) §4。
> 大型项目即 `ROVE_TEST_UNITY_LARGE`（242 个 csproj、21,221 个文件），源码在 SATA SSD（Samsung 870 EVO）上；机械硬盘为 ST2000DM001。

## 结论

| 指标（大型项目） | 优化前（M0 进程） | 优化后 | 目标 |
|---|---|---|---|
| 热缓存总耗时，机器空闲时 3 轮交替 | 74.5 / 75.4 / 77.8 s | 72.4 / 72.8 / 75.0 s | < 90 s ✅ |
| 热缓存总耗时，同机有其他构建时 | 95–114 s | 84–103 s | |
| 峰值工作集 | 4.8–5.0 GB | 2.66–2.93 GB | < 3 GB ✅ |
| 冷缓存，SSD | 81.7 / 97.4 s | 88.5 s（另一轮 64.7 s） | |
| 冷缓存，机械硬盘 | 86.6 / 179.8 s | 91.4 / 91.7 s | |
| 写索引 | 11.7–18.5 s | 4.1 s | |
| 中型项目（`ROVE_TEST_UNITY_MEDIUM`） | 51.7 s / 2.0 GB | 41.0 s / 1.5 GB | |

- **两项验收都达到了。** 耗时的余量主要来自写索引（18 s → 4 s）和读文件与绑定重叠。降内存主要靠"项目绑定完即释放"。
- M0 测得的 118 s / 5.5 GB 是另一时段的数据。本机空闲时，M0 进程本身也只要 75 s；但只要同机还有其他编译在跑，它就会涨到 95–114 s。新进程在同样的干扰下是 84–103 s。
- 冷读取不再是瓶颈：读文件与解析、绑定完全重叠。机械硬盘上冷启动比热缓存只多 15–20 s，前提是并发度够深（见 §3）。
- 本机测量受同机其他会话的 cargo 构建与测试干扰，单次运行的波动可达 ±15%。表中给出多次运行的范围，交替运行的 A/B 才可直接比较。
- 索引内容与 M0 等价（§4），且同样的输入两次产出逐字节相同的索引文件。

## 1. 剖析（先剖析，再动手）

本机没有安装 `dotnet-trace` / `dotnet-counters`（需要从 NuGet 下载全局工具）。所以剖析改为在进程内做：逐个调用累计线程秒、定点强制 GC 后读取存活量、按数据结构依次释放并测差值。下面的数字都来自 M0 进程加上这些计时（保留为 `--profile`）。

**绑定阶段 67–76 s 花在哪里**（16 线程合计 1208 线程秒）：

| 部分 | 线程秒 | 占比 |
|---|---|---|
| `GetSymbolInfo`（含语义模型首次绑定方法体） | 934 | 77% |
| 我们自己计算符号键（每个出现位置都重新生成文档注释 ID 字符串并查字典） | 147 | 12% |
| `GetDeclaredSymbol` | 41 | 3% |
| 关系收集 | 24 | 2% |
| 遍历语法树、坐标换算、列表追加 | 62 | 5% |

`GetSymbolInfo` 无法再拆：对方法体内的名字，首次调用会绑定整个方法体并缓存，之后的调用只是查表。我们的遍历只访问 `SimpleNameSyntax` 和声明节点，关键字、字面量、标点、注释本来就不会触发 `GetSymbolInfo`。所以 issue 里"跳过不可能引用符号的节点"这一项没有可省的调用。

**内存都在哪里**（绑定结束时工作集 4.2 GB，存活 3.1 GB；写索引阶段再涨到 5.0 GB）：

| 部分 | 存活量 |
|---|---|
| 语法树（绿树 + 遍历留下的红树）、源码文本、坐标表 | 1,275 MB |
| 242 个编译与其中的符号缓存 | 540 MB |
| 符号表与字符串（96 万个符号） | 520 MB |
| 出现位置列表：580 万条，但容量是 2,400 万条（每文件预分配 1024，4 倍浪费） | 460 MB |
| 其余（DLL 元数据等） | 330 MB |

**GC**：服务器 GC，16 个堆。绑定结束时第 0/1/2 代与 LOH 分别为 0 / 254 / 2,827 / 91 MB，回收次数 55 / 26 / 16，暂停占 7.3%。工作集比存活量多出约 1 GB，这部分是服务器 GC 的余量。

结论：内存的大头是"所有项目的语法树和编译同时活着"。CPU 的大头是 Roslyn 的绑定本身；我们能省的是符号键计算（12%）和写索引（18 s）。

## 2. 做了什么、为什么

1. **按依赖拓扑的项目流水线，上下游用元数据镜像解耦。**
   - 每个项目依次经过：读文件 → 解析 → 构造编译 → 输出 metadata-only 镜像 → 绑定。下游只引用上游的镜像，不持有上游的 `Compilation`，所以一个项目绑定完，它的语法树、编译和语义缓存都能立即回收。
   - 经元数据看到的参数（命名实参、以实例形式调用的扩展方法）没有源码位置。这些参数按"所属成员的文档注释 ID + 序号"记下，写索引时回指源码声明，与 M0 的局部键一致。
   - 镜像输出失败时，下游退回引用编译，语义与 M0 相同。大型项目里的 ScriptGame 就是这种情况：csproj 声明 C# 9，代码用了 C# 10 的结构体字段初始化器；即使 `tolerateErrors`，Roslyn 也拒绝输出。按高语言版本重建编译再输出也可行，但要把整套声明绑定重做一遍，在这个最大的项目上要多花 10 s 以上，所以没有采用。
2. **关键路径调度。**
   - 项目优先级 = 自身文件数 + 下游最长链上的文件数。
   - 同时活着的项目受文件数上限约束（`--max-active-files`，默认 6000）。关键路径上的项目（优先级不低于任何尚未开工的项目）不受这个上限约束。
   - 前段（读取、解析、编译、镜像）在线程池上临时提到高于正常的优先级；绑定拆成逐文件工作项，交给按优先级排队的专用线程。
   - 依据：只按拓扑顺序而不按优先级时，CPU 平均只用了 16 个逻辑核中的 7.5 个。ScriptAuto 在上游镜像就绪后又等了 24 s 才排上队。
   - 绑定线程不能降到低于正常优先级：同机有其他编译时，它们会被饿死（实测 CPU 利用率降到 5.6 核）。
3. **读取与解析流水线，并发度可配。** 预读线程按模拟出的开工顺序读文件（`--io-concurrency`，默认 32；`--prefetch-mb`，默认 256），与解析和绑定重叠。并发度的实测见 §3。
4. **每个编译一份 ISymbol → 符号记录的缓存。** 同一编译里第二次遇到同一个符号时，不再生成文档注释 ID。符号键的开销从 147 降到约 98 线程秒，剩下的是每个项目第一次见到某个符号时的开销。
5. **写索引不再依赖语法树。**
   - 不生效区间改为沿预处理指令链收集，不再遍历整棵树的 trivia。
   - 按符号的出现位置索引改为计数排序，不再建 96 万个 `List<uint>`。
   - 符号排序用并行排序。文件内排序并行进行。各段整段按字节写出。
   - 写索引从 11.7–18.5 s 降到 4.1 s。
6. **内存。**
   - 出现位置改为每个文件一个定长数组（460 → 111 MB）。
   - 成员的容器键、参数登记表复用符号记录里的同一个字符串实例，符号表从 614 MB 降到 331 MB。
   - 流水线结束时留存 567 MB（M0 写索引前是 3.1 GB）。
7. **GC。**
   - 已释放的项目数据活得够久，已晋升到第 2 代，服务器 GC 要等第 2 代预算涨满才回收。为此每释放约 1500 个文件的项目，就主动发起一次后台完整 GC（`--gc-every-files`）。
   - 另设软上限（`--soft-memory-mb`，默认 2200）：工作集超限时做一次激进的压缩 GC，把空闲段还给系统。
   - 软上限每次运行触发约 8–10 次，代价约 4–5 s；不开时峰值为 3.25 GB。
8. **没有采用的方向（数据不支持）。**
   - 流式写入临时段再归并：紧凑后的出现位置只有 111 MB，写索引已降到 4 s，再分段只会增加 I/O。
   - 字符串驻留：剩余可省的约 60 MB，不再需要。
   - GC 配置：工作站 GC 慢 50%，内存反而更高；`GCConserveMemory`、DATAS、`GCgen0size` 对峰值都没有改善；`GCHeapCount=8` 有时更快，但峰值更高。默认配置不变。

## 3. 冷启动 I/O

**测量方法**：清系统缓存需要管理员工具，所以改为用 `FILE_FLAG_NO_BUFFERING` 打开每个源文件一次。NTFS 会因此清掉该文件的缓存页；目录元数据仍在缓存里，所以这里的"冷"比重启后略暖。机械硬盘的数据，是把源码用 `robocopy /J`（无缓冲 I/O）复制到 HDD 后测的。

| 磁盘 | 进程 | 并发度 | 总耗时 |
|---|---|---|---|
| HDD | 新 | 1 | 328.4 s |
| HDD | 新 | 4 | 159.9 s |
| HDD | 新 | 16 | 102.7 s |
| HDD | 新 | 32 | 91.7 / 91.4 s |
| HDD | 新 | 64 | 91.3 s |
| HDD | M0 | 线程池（不设上限） | 86.6 / 179.8 s |
| SSD | 新 | 1 | 104.1 s |
| SSD | 新 | 4 | 94.3 s |
| SSD | 新 | 16 | 90.9 s |
| SSD | 新 | 32 | 64.7 / 88.5 s |
| SSD | M0 | 线程池 | 97.4 / 81.7 s |

- **和 issue 里的预期相反：机械硬盘上并发越深越快。** 同时只发一个请求时，每个小文件都要付一次完整的寻道与旋转延迟；队列深了，磁盘的 NCQ 和系统 I/O 调度才能把请求按磁头位置重排。32 之后不再改善，默认值定为 32。
- 冷缓存下，新进程在 HDD 上稳定在 91 s 左右，比热缓存多 15–20 s。M0 进程先把所有文件读进内存再开工，两次测量相差一倍（同一块盘上还有其他会话的工作区）。
- 这些数字包含同机其他负载的干扰。HDD 的结果是相对较稳定的那组。

## 4. 等价性与确定性

- 用一个脚本把索引规范化为与符号编号无关的文本：按文件列出出现位置及其符号键，按键列出符号记录与关系。
- 大型项目上，与 M0 进程相比，文件、出现位置（580 万条）、关系三部分**零差异**。差异只出现在约 200 行符号记录的元数据上，分三类：
  - 匿名类型成员、元组元素字段、`?` 后备键这类真正撞键的情形，M0 取先到者（每次运行都可能不同），现在取确定的最小值；
  - 命名空间的"存在源码位置"标志，现在只要任一项目在源码里声明了这个命名空间就置位；
  - 元组元素字段在另一项目的源码里命名时，经元数据看不到它的源码位置。
- 中型项目同样零出现位置差异。
- M0 进程自己两次运行之间，就有 7 条符号记录不同（撞键取先到者）。新进程两次运行的索引文件**逐字节相同**。
- 端到端测试 `cross_project_parameters_resolve_through_metadata_images` 覆盖了跨项目的命名实参、扩展方法参数、镜像失败回退，以及输出确定性。

## 5. 源生成器

- **M0 生成 0 个文件的原因是生成器根本没有加载成功。** M0 用默认加载上下文直接加载生成器 DLL；Entities 的生成器依赖同目录下的 `Common.dll` 等程序集，解析不到时，生成器在 `GetGenerators` 或运行阶段静默失败，诊断信息被丢弃。
- 现在每个分析器目录使用独立的加载上下文，依赖从同目录解析，Roslyn 与运行时程序集与宿主共享；加载失败和生成器诊断都会写进 `--report` 的 `generator_issues`。
- 同一大型项目开启 `--generators` 后：
  - 生成了 17 个文件，全部来自 Entities 的 `SystemGenerator` 与 `AspectGenerator`（`Unity.Entities`、`Unity.Scenes`、`Unity.Transforms` 等包里的 `ISystem` 实现）；M0 进程同样参数下仍是 0。
  - `Unity.Properties.SourceGenerator` 加载成功但没有产出：项目里虽然有 `[GeneratePropertyBag]`，但没有程序集声明 `[assembly: GeneratePropertyBagsForAssembly]`，这个生成器不会运行。
  - 未解析名称占比不变（0.0624%）；生成器消耗约 89 线程秒，总耗时 +约 7 s。
- **结论：`--generators` 默认关闭。** 建议打开的情形：用户代码直接引用生成的成员，例如 Entities 的 Aspect（`MyAspect.Lookup`、`TypeHandle`）或 `[GeneratePropertyBag]` 生成的属性包；或者需要在生成代码里跳转。结论已写入 [LANGUAGE_INTELLIGENCE](LANGUAGE_INTELLIGENCE.md) §3.3。

## 6. 复现

```bash
dotnet build tools/rove-indexer-cs -c Release
dotnet tools/rove-indexer-cs/bin/Release/net9.0/rove-indexer-cs.dll <unity-project> out/x.idx --report out/x.json
# 剖析：每 3 秒强制 GC 打印存活量、项目时间线、写索引分步耗时
dotnet tools/rove-indexer-cs/bin/Release/net9.0/rove-indexer-cs.dll <unity-project> out/x.idx --profile
# 端到端测试（需要先完成上面的 Release 构建）
cargo test -p rove-lang-cs -- --include-ignored
```

`--report` 新增字段：`thread_seconds`（读取、解析、编译、生成器、镜像输出、绑定及其拆分）、`cpu_seconds`、`peak_gc_heap_mb`、`peak_gc_committed_mb`、`gc_collections`、`gc_pause_percent`、`soft_limit_collections`、`options`、`read_bytes`、`metadata_images`、`metadata_image_fallbacks`、`generator_issues`。原有字段保留。阶段耗时 `phases_ms` 改为 `parse_csproj`、`index_projects`、`write_index`：读取、解析、编译与绑定在流水线中重叠，不能再分段计墙钟时间，各自的 CPU 去向见 `thread_seconds`。

由于阶段行不再按 M0 的 `[parse_syntax]` / `[bind_and_collect]` 输出，进程在 stderr 上改为每完成 1% 的文件绑定输出一行 `progress <已绑定> <总数>`。这是 #36 的索引生命周期（`Progress::parse`）预留的协议，进度条直接采用。进程版本 1.0.3 与 #36 的 `EXPECTED_INDEXER_VERSION` 同步更新。
