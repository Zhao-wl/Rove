# Rove 语言智能设计（C#）

> 版本：v0.1（草案） · 日期：2026-11-09

## 1. 目标

| 能力 | 准确性要求 | 响应要求 |
|---|---|---|
| 定义跳转（含成员、局部变量、外部 DLL 符号） | 与编译器一致 | < 16 ms |
| 查找引用 | 与编译器一致，不能出现同名噪音 | < 50 ms |
| 查找实现 / 重写 / 基类成员 | 与编译器一致 | < 50 ms |
| 悬停：类型、签名、XML 文档注释 | 与编译器一致 | < 16 ms |
| 工作区符号搜索 | 模糊匹配 | < 30 ms |
| 高亮、大纲、折叠 | 语法级 | 每次按键 < 2 ms（增量） |

同时要求：**常驻内存低**、**打开项目后几秒内就有可用的导航**。

## 2. 为什么之前的“两档方案”不够

### 2.1 纯语法索引（tree-sitter + 按名称解析）的天花板

它只认识“名字”，不认识“类型”。在 C# 中以下情况都会出错：

| 场景 | 示例 | 按名称解析的结果 |
|---|---|---|
| `var` 类型推断 | `var p = GetPlayer(); p.Move();` | 不知道 `p` 的类型，`Move` 只能列出所有同名方法 |
| 链式调用 | `a.GetB().GetC().Run()` | 每一步都要知道返回类型，基本无解 |
| 方法重载 | `Log(int)` / `Log(string)` | 无法区分 |
| 继承与重写 | `base.Init()`、`override`、接口实现 | 需要完整的继承链和成员查找规则 |
| 扩展方法 | `list.Where(...)`、自定义 `transform.Reset()` | 需要知道接收者的类型，以及哪些静态类被 `using` 引入 |
| 泛型 | `GetComponent<T>()`、`Dictionary<K,V>` 的值类型 | 需要泛型替换与推断 |
| Lambda / LINQ | `items.Select(x => x.Id)` | `x` 的类型来自委托推断 |
| 条件编译 | `#if UNITY_EDITOR` | 需要知道当前生效的宏 |
| 外部程序集 | `Transform.position`、BCL、第三方 DLL | 源码里不存在，必须读取元数据 |

**对 Unity 项目最致命的是“查找引用”**：`Update`、`Init`、`OnEnable`、`Value`、`Get` 这类名字在项目中会出现成百上千次。按名称查引用，结果几乎全是噪音，完全不可用。

因此，纯语法索引只适合做：高亮、大纲、折叠、类型名跳转、工作区符号搜索。它**无法**承担成员级跳转和查找引用。之前文档里写的“约 90% 准确率”过于乐观，这里更正。

### 2.2 常规 LSP（Roslyn Language Server / OmniSharp / csharp-ls）的问题

LSP 的准确性没有问题（底层都是 Roslyn 编译器），问题在于**它是一个“实时计算”模型**：

| 问题 | 说明 |
|---|---|
| 常驻内存高 | 需要把整个解决方案的编译模型一直放在内存里，中大型 Unity 项目通常要 1–3 GB |
| 冷启动慢 | 要通过 MSBuild 加载解决方案，大项目需要 30 秒到数分钟，期间完全没有导航 |
| 查找引用慢 | 每次请求都要在全解决方案中实时搜索，大项目经常需要数秒 |
| 每次打开都重来 | 关闭编辑器后没有持久化，下次打开又要冷启动 |
| 依赖 MSBuild 环境 | 需要安装 .NET SDK，并保证解决方案能被正确加载 |

它能满足准确性，却满足不了 Rove 最看重的**响应速度**和**轻量**。

## 3. 推荐方案：预计算的精确语义索引

核心思路：**让编译器离线把所有答案算好，Rove 只负责查表。**

- 准确性来自 Roslyn（与编译器完全一致）
- 响应速度来自查表（索引文件内存映射，跳转和引用都是 O(log n) 查找）
- 内存低：Roslyn 进程只在建索引时运行，建完就退出；Rove 主进程只映射索引文件
- 持久化：索引缓存在磁盘上，第二次打开项目时立即可用

这和 Sourcegraph 的 SCIP、Kythe、Google 内部的代码搜索属于同一类思路，在大规模代码阅读场景中已被验证过。（Sourcegraph 有基于 Roslyn 的开源实现 `scip-dotnet`，可作为参考，许可证需在 M0 确认。）

### 3.1 三层结构

```
┌──────────────────────────────────────────────────────────────┐
│ L2 语义索引（精确）                                            │
│   Roslyn 索引进程离线生成 → 磁盘索引文件 → Rove 内存映射查询     │
│   定义 / 引用 / 实现 / 重写 / 悬停 / 外部 DLL 符号              │
├──────────────────────────────────────────────────────────────┤
│ L1 快速声明索引（近似，Rust 实现）                              │
│   tree-sitter 扫描全工作区的声明，打开项目后几秒内可用            │
│   类型名跳转、符号搜索、L2 未就绪或文件已修改时作为回退           │
├──────────────────────────────────────────────────────────────┤
│ L0 语法层（tree-sitter，增量）                                 │
│   高亮、折叠、大纲、当前文件内的局部变量与参数跳转                │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 查询路由

```
请求（文件, 位置）
  ├─ 文件内容与 L2 索引时的版本一致？
  │     是 → 查 L2 → 精确结果
  │     否 → 已修改文件做位置映射（按文本 diff 平移行列）
  │            ├─ 映射成功且该符号所在区域未被修改 → 查 L2
  │            └─ 否则 → L0/L1 回退，结果标记为“近似”，
  │                     并触发该文件的增量重建
  └─ L2 尚未建好 → L0/L1 回退，界面提示“语义索引构建中 xx%”
```

用户总能**立即**得到结果；L2 就绪后，结果自动变为精确。

### 3.3 Roslyn 索引进程（`rove-indexer-cs`）

**项目模型：不走 MSBuild，直接构造编译。**

- Unity 生成的 `.csproj` 结构固定，直接解析即可：`Compile` 文件列表、`Reference` 的 `HintPath`、`DefineConstants`、`ProjectReference`。
- 解析结果用来构造 Roslyn `AdhocWorkspace` / `CSharpCompilation`，绕开 MSBuild，速度快，也不依赖 SDK 环境。
- 没有 `.csproj` 时的回退（Unity 尚未生成项目文件）：读取 `*.asmdef` 划分程序集，引用 `Library/ScriptAssemblies` 和 Unity 安装目录下的托管 DLL。
- 普通 .NET 项目（SDK 风格的 `.csproj`）：先尝试简易解析，失败再走 MSBuildWorkspace。

**索引内容：**

| 数据 | 用途 |
|---|---|
| 符号表：符号 ID、种类、名称、容器、签名、文档注释、定义位置 | 跳转、悬停、符号搜索 |
| 引用表：符号 ID → 位置列表（标注读/写/调用/继承） | 查找引用 |
| 关系表：实现、重写、基类型、派生类型 | 查找实现、类型层级 |
| 外部符号：来自 DLL 元数据的签名与文档 | 跳转到外部符号时显示只读的“元数据视图” |
| 每个文件的内容哈希 | 判断索引是否过期 |
| 非活动预处理区域 | 把 `#if` 中未生效的代码置灰 |

**增量更新：**

- 索引进程在空闲 N 分钟后退出；有文件变更时由 Rove 重新拉起（或在一段时间内常驻）。
- 文件保存后：重新分析该文件，更新“该文件发出的引用”和“该文件声明的符号”。Roslyn 的增量编译使单文件分析通常在百毫秒级完成。
- 如果某个符号的签名或可见性变了，可能影响其他文件的绑定，这时把受影响的文件加入后台队列逐步重建。
- 定期（或在 git 切换分支、大量文件变化时）后台全量重建，并原子替换索引文件。

**Source Generators（`--generators`，默认关闭）：**

- 每个分析器目录使用独立的加载上下文，依赖从同目录解析。M0 用默认加载上下文，Entities 生成器的依赖解析不到，所以静默失败、生成 0 个文件。
- 修正后，在大型项目上实测：Entities 的 `SystemGenerator` / `AspectGenerator` 为 `ISystem` 实现生成了 17 个文件。`Unity.Properties` 的生成器加载成功，但没有程序集声明 `[assembly: GeneratePropertyBagsForAssembly]`，所以没有产出。未解析名称占比不变，耗时约 +7 s。
- 默认关闭。以下情形建议打开：用户代码直接引用生成的成员（Entities 的 Aspect `Lookup` / `TypeHandle`、`[GeneratePropertyBag]` 生成的属性包等），或者需要在生成代码里跳转。
- 数据见 [M2_INDEXER_PERF_REPORT](M2_INDEXER_PERF_REPORT.md) §5。

**分发：**

- 以 self-contained 方式发布，内置 .NET 运行时，用户无需安装 SDK。体积估计 60–90 MB，所以作为可选组件，与主程序（< 30 MB）分开。（已确认接受，2026-11-09）
- 主程序没有这个组件也能运行，只是 C# 导航停留在 L0/L1。
- 打包、安装位置、发现规则、版本握手与 trim 结论见 [CS_INDEX_FORMAT](CS_INDEX_FORMAT.md)「组件、协议与索引格式的版本」「组件包与安装约定」（#43）。

### 3.4 L1 快速声明索引（Rust）

- 并行扫描所有 `.cs` 文件，用 tree-sitter 提取命名空间、类型、成员声明（含 partial 聚合）。
- 1 万个文件的项目目标 < 3 秒，结果持久化，后续打开时增量更新。
- 负责的能力：工作区符号搜索、按“命名空间 + 类型名”跳转、L2 不可用时的候选列表（明确标注为“近似”）。

## 4. 方案对比

| 维度 | 纯语法索引 | 常规 LSP | **预计算语义索引（推荐）** |
|---|---|---|---|
| 成员跳转准确性 | 低 | 精确 | 精确 |
| 查找引用准确性 | 不可用（同名噪音） | 精确 | 精确 |
| 跳转/引用响应 | 快 | 跳转快，引用慢（秒级） | 极快（查表） |
| 首次打开可用时间 | 秒级 | 30 秒到数分钟 | 秒级（L1），L2 后台完成 |
| 再次打开可用时间 | 秒级 | 30 秒到数分钟 | 立即（磁盘缓存） |
| 常驻内存 | 低 | 1–3 GB | 低（索引按需映射） |
| 编辑中的实时准确性 | — | 最好 | 已修改区域降级为近似，保存后恢复 |
| 实现成本 | 低 | 低（集成为主） | **高** |

**主要代价**：

1. 实现成本高：索引格式、增量策略、位置映射、项目模型解析都需要自己做。
2. 正在编辑但未保存的代码，导航精度会下降（Rove 以阅读为主，编辑为辅，这个代价可以接受）。
3. 需要随产品附带 .NET 组件。

## 5. 不在首版范围

- 代码补全、实时诊断（错误红线）、重构、代码修复：这些依赖实时语义模型，与“阅读优先、轻量”的定位冲突。后期如有需求，可以按需拉起 LSP，只用于补全和诊断。
- Unity 资源引用（脚本被哪些 prefab/scene 通过 GUID 引用）：对游戏开发很有价值，列入后期候选。

## 6. 验证计划（M0 的一部分）

在 1–2 个真实 Unity 项目（中型约 3 千个 `.cs` 文件，大型约 1 万个以上）上验证：

| 验证项 | 通过标准 |
|---|---|
| 不依赖 MSBuild 构建编译，错误率 | 绑定失败的符号 < 1% |
| 全量索引耗时 / 峰值内存 | 大型项目 < 90 秒 / < 3 GB（索引进程，可退出） |
| 索引文件大小 | < 200 MB |
| 单文件增量更新耗时 | < 300 ms |
| Rove 侧查询响应 | 跳转 < 16 ms，引用 < 50 ms |
| 导航准确率测试集 | 人工整理约 200 个典型用例（var、扩展方法、重载、泛型、继承、Unity API），精确层 100% 正确 |

验证不达标时的退路：改为“按需拉起 Roslyn LSP + 结果缓存”的方案。
