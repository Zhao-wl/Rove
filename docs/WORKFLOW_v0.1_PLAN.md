# v0.1 剩余工作的执行工作流

> 2026-11-13 · 覆盖 GitHub 里程碑「v0.1 首发」的全部 34 个未关闭 issue。**已确认**，确认结果记在第 6 节；第 6 节与前文冲突时，以第 6 节为准。

## 1. 总体设计

用**同一个工作流脚本**分四个波次运行：每个波次跑完都停下来，把结果和需要人工处理的事项交给你，你确认后再启动下一个波次。
不做成一次跑到底，原因有两个：后面的波次要依赖前面合并进 main 的结果；另外有几项验收必须由人来做，比如输入法实机测试、多显示器、干净虚拟机安装。

每个 issue 依次经过五个阶段（同一波次内用 pipeline 推进，issue 之间互不等待）：

| 阶段 | 做什么 | 隔离与资源 |
|---|---|---|
| ① 实现 | 读 issue 正文与 `AGENTS.md`，从最新 main 建分支 `issue/<编号>-<短名>`，实现功能，补集成测试，替换 `SKELETON`，更新 `ARCHITECTURE.md` 对照表，只在受影响的 crate 上跑 fmt / clippy / test，提交 | 独立 worktree；占用 1 个构建槽 |
| ② 独立审查 | 另起一个代理，**不看实现者的总结**，只看 diff 和 issue：逐条核对验收标准、`AGENTS.md` §5 完成标准（登记机制、不写死、不修改契约、无网络、性能数据），找正确性问题 | 只读，不占构建槽 |
| ③ 修复 | 有问题就交回实现者修复，再审一次；**最多两轮**，还过不了就标为「需要人工」，退出流水线 | 占用 1 个构建槽 |
| ④ 合并队列 | **全局串行**：rebase 到最新 main（`Cargo.lock` 冲突按 `AGENTS.md` §6 处理），跑全量的 fmt、`clippy -j 2`、`test --workspace -j 1`、`check-core-crates`、`check-eol`，然后推送、建 PR（`Closes #n`，逐条勾选验收标准）、squash 合并 | 同一时间只有一个合并在进行，保证 main 始终可编译 |
| ⑤ 收尾 | 记录结果：已合并 / 需要人工 / 被阻塞，并写明原因 | — |

**构建槽**：本机内存紧张（`cargo test` 要用 `-j 1`），脚本里用一个信号量限制**同时只有 2 个代理在编译**，合并队列也占一个。
所有构建命令统一带上降内存设置：`-j 1` / `-j 2`、`_LINK_=/DEBUG:NONE /INCREMENTAL:NO`、`CARGO_PROFILE_*_DEBUG=0`；release 和 bench 构建关掉 LTO。
编码的并行度因此被限制在 2；审查不编译，可以多开。

**模型与 effort**：难度 3–4 的 issue 和集成验收用高 effort，难度 1–2 用默认值；审查一律用高 effort。

## 3. 每个波次结束时交给你的东西

- 合并结果表：issue、PR、合并提交、在哪台机器的什么负载下验证；
- **需要人工的事项清单**：自动审查两轮仍没过的问题、性能数据只能在空闲机器上测的条目、输入法实机测试、多显示器、截图对照、干净虚拟机安装；
- 新发现的问题：只开 issue，不在当前 PR 里顺手修。

## 4. 代理不会自己做、要你来的事

| 事项 | 时间 | 原因 |
|---|---|---|

| 性能复测时关掉 Unity，让机器空闲 | 波次 2 集成验收时 | #117 #125 #126 #132 #133 的最终数字要在空闲机器上测 |

| 干净 Win10 / Win11 虚拟机上安装、自动更新、卸载 | 波次 3 | 需要虚拟机 |
| 发布正式 Release v0.1.0（公开可见） | 波次 3 结束 | 对外发布 |

## 5. 规模与成本

- 子代理约 **130–170 次**：34 个 issue，每个平均 3–4 次（实现、审查、修复、合并），再加上集成验收。这远超默认的「10 个代理以内」，是你明确要求了完整工作流才这样安排的。
- token 消耗会很大，按百万计。波次 1 最重，大约占一半。
- 实际耗时主要卡在构建槽上（同时只有 2 个在编译）。

## 6. 确认结果（2026-11-13）

| 事项 | 决定 |
|---|---|
| 审查后的问题 | 分成**阻碍性**和**非阻碍性**两类。阻碍性的必须修复，最多修两轮；还修不好就不合并，依赖它的下游 issue 跳过。非阻碍性的不修，**最后统一汇总** |
| 合并 | **工作流自动合并**（squash），条件是没有阻碍性问题、本地全量检查全绿。本次 v0.1 工作不适用 `AGENTS.md`「会话只提 PR」的规则 |
| 发布 | #76 同时提供本地发布命令：`cargo xtask release` 生成产物并给更新清单签名，`gh release create` 上传。Actions workflow 照常写好，额度恢复后就能用。工作流**不打 tag、不发布 Release** |
| 性能 | 各 issue 只要求附优化前后的相对数据，并注明机器负载；空闲机器上的最终复测放进最后的人工清单 |
| 波次之间 | **不停下来等确认**，按依赖关系自动往下推进；遇到阻碍性问题时，只跳过受影响的下游 |

**阻碍性问题**：
- 构建、clippy 或测试失败；
- 核心功能或主要验收标准不成立；
- 数据丢失、崩溃、结果错误；
- 违反硬约束：更新模块以外出现网络请求、读取 `.gitignore`、核心层依赖 gpui、在 PR 里顺手改契约；
- 导致其他已有功能退化。

**非阻碍性问题**：风格与命名、次要的测试缺口、负载下测出的性能数字、需要人工或空闲机器才能完成的验收项、文档小问题。

**调度方式**（取代第 2 节的「每个波次结束都停下」）：每个 issue 的前置依赖一合并就开工，不必等整个波次结束。三个集成验收人为排成 #31 → #44 → #51 依次执行，避免同时跑真实 Unity 项目。

**更新签名密钥**：#76 在本机生成 ed25519 密钥对。私钥放在仓库之外（`%LOCALAPPDATA%\Rove-release\update-signing.key`），不提交、不打印；公钥提交进仓库。私钥的备份、存入 Actions secret 列进最后的人工清单。
